今天下午在杭州听了一下午搜索相关的分享，四场：动态本体落地、阿里云 AI 搜索方案、向量搜索与 Elasticsearch、Elasticsearch 的应用场景。

去之前我以为会听到四套不一样的东西，听完发现是同一件事的四种叫法——**怎么把企业里散着的数据，变成智能体能用的语义结构**。业务侧叫「动态本体」，平台侧叫「上下文引擎」，检索侧叫「混合搜索」，底座都是同一个：Elasticsearch。

这篇不复述 PPT。我按「哪些能直接用、哪些只是话术、哪些是我自己回去要改的」来写。

## 一、先把结论放前面

1. **搜索没有被 AI 取代，是被叠加了。** 现场那张演进图最后一句话是「不是替换，而是叠加：Elasticsearch 永远是底座，LLM 负责理解与表达，规则与词典负责可控」。这句话我认。
2. **单路调参有天花板，多路融合是结构解法。** 现场给的数字：单路最高 80.38%，融合后 84.10%。四个点看着不多，但那是在单路已经调不动的地方拿到的。
3. **向量不是免费的。** HNSW 要全量进内存，1536 维 float32 一条就是 6KB 左右，千万级就是几十 GB。省内存靠量化，保精度靠过采样＋重排，这两件事必须成对做。
4. **上下文工程的瓶颈不是「取不到」，是「取太多」。** 100 万 token 的窗口不是解法，注意力会被稀释，前后还会自相矛盾。
5. **语义层的门槛不在模型，在你敢不敢把业务规则写成可编排的一层。** 这条是我这次最难受的一条，后面细说。

## 二、从关键词到导购智能体：四级演进

![搜索到智能体：四级演进 + 四路召回](/images/2026-11-28-semantic-search/fig1-search-to-agent.jpg)

现场把搜索到智能体的路径拆成四级：

- **L1 关键词搜索**：字面匹配，靠分词和倒排。优势是可控、可解释、聚合统计强。
- **L2 语义搜索**：Embedding + 同义理解，落法是 `dense_vector` + kNN。解决「说法不一样但意思一样」。
- **L3 对话式搜索**：LLM 多轮对话，把用户的模糊需求问清楚。ES 在这里的角色是 filter 和聚合——用聚合结果驱动下一轮追问。
- **L4 导购智能体**：工具、澄清、决策、反馈，四件事都要有。ES 的角色变成多路召回 + 融合 + 日志回流。

四级不是「新一代干掉上一代」。L4 里如果没有 L1 的精确匹配，用户搜「iPhone 15 Pro 256G 原色钛金属」这种型号规格，向量是接不住的——现场讲者的原话是「向量对型号和数字规格不敏感」。

我自己的判断：**L4 的门槛不在模型，在能不能把业务规则写进检索。** 预算 500 元、门店有货、只推荐当季，这些不是语义相似度能算出来的，得变成过滤条件和打分项。

## 三、四路召回：每一路都有一类它接不住的问题

同一场里还有一张图，把「四路召回」摊开讲得很干净：

| 召回路 | 索引 | 擅长 | 短板 |
|---|---|---|---|
| 关键词 BM25 | `sku_search_index` | 品牌、型号、规格等字面匹配 | 同义词与口语表达 |
| 向量 kNN | `dense_vector`（4096 维，cosine） | 口语化、同义、泛需求 | 对型号和数字规格不敏感 |
| 个性化·历史 | `historical_recall_index` | 同类需求以前选过什么 | 冷启动、全新需求无历史 |
| 实体召回 | `sku_entity_search_index` | NER 槽位对齐商品索引实体字段 | 依赖 NER 抽取质量 |

这张表的价值不在「有四路」，在于**它承认每一路都有明确的失效场景**。承认短板，才谈得上融合。

还有一个工程细节我很喜欢：这四路自带超时与降级，某一路失败只记为降级，不拖垮整条链路。这句话听着平淡，做过搜索的人知道有多重要——一次 kNN 超时把整个请求拖死，是线上最常见的事故形态。

## 四、单路 80.38%，融合 84.10%：那四个点是怎么来的

现场给的经验是：多路召回比单路调参更稳，单路最高 80.38%，融合后 84.10%。

我不打算把这四个点吹成「巨大提升」。它真正的含义是：**当你已经把单路的参数调到尽头，继续调是收益递减的；换结构才有增量。**

融合这块，现场讲了一个很多人踩过的坑：**分数量纲不可比**。BM25 的分数可以到一万、几万，cosine 相似度只有 0 到 1。你直接把两种分数加权相加，等于让 BM25 单方面决定排序。

解法是 RRF（Reciprocal Rank Fusion）——不看分数，看名次。每一路给出自己的排名，按 `1/(k+rank)` 累加。好处是稳定、不需要归一化、不需要为每一路调一个权重系数。

现场还有两句我抄下来了：

- **融合用名次，权重进配置。** 权重不要写死在代码里，放配置，线上可调。
- **一切可回放。** 冻结配置 + 全链路轨迹，优化才有依据。没有回放能力，你调完参数不知道是变好了还是碰巧。

## 五、向量不是免费的：先算内存账，再谈方案

这一段是我这次收获最硬的技术细节。

HNSW 的问题是要把向量全量放进内存。1536 维、float32，一条向量 1536×4 = 6144 字节，大约 6KB。一千万条就是 60GB 上下——这还没算图结构和副本。

现场的演进路径是这样的：

1. **全内存 HNSW**：最准，最贵。
2. **部分落盘**：把一部分结构放到磁盘，换内存。
3. **INT8 量化**：4 字节压到 1 字节，内存降到大约四分之一。
4. **INT4**：再压一半。
5. **BBQ（1 bit）**：再压一个数量级，讲者说能省到 95% 的内存。

压缩一定会掉精度。所以必须配两个动作：

- **过采样**：候选从 100/200 放大到 1000/2000，先把可能被压丢的捞回来。
- **rescore / re-rank**：用原始向量（或更高精度的表示）对这小撮候选重算距离，把掉到第 100 位的拉回第 1 位。

这套组合的本质是：**用召回率换成本，再用重排把精度买回来。** 这句话可以迁移到很多地方，不只是向量检索。

给要做这件事的人一句提醒：**先算内存账，再选量化方式。** 量化不是「省钱的优化」，是「装不装得下」的前提。顺序反了，会做出一个跑不起来的方案。

## 六、上下文工程：100 万 token 不是答案

第三场讲到上下文工程，有一段我觉得比技术细节更值钱：

窗口开到 100 万 token，不代表问题解决了。信息一多，会出现四件事——上下文溢出、token 烧得快、注意力分散、前后不一致甚至自相冲突。

这四件事我在自己的 RAG CLI 上全踩过。文档切得多一点，召回多一点，模型就开始「综合」出一段谁也没说过的话。

现场给的几个方向，我挑能落地的三条：

- **记忆分层**：短期（当前会话）、长期（用户偏好与事实）、会话级（这一次任务的中间状态），三层分开存、分开检索。全塞进一个向量库是最省事也最差的做法。
- **大文档用目录检索**：不要无脑按 512 token 切块。给文档建一层层级目录（章节、小节），检索先定目录再进正文。讲者的说法是配置式的层级目录、不走向量，效果比传统分块好。
- **不要每次提问都重新编排整条查询路径**：每次重排，解读就不一致，知识也容易孤岛化，token 还费。

一句话总结这一节：**RAG 的瓶颈不在「取不到」，在「取太多」。**

## 七、业务本体：对象 + 规则 + 行动

第一场讲「动态本体」，讲者是做了二十多年数据库的人，2023 年转去做企业 AI。他开场那句话很扎人：

> 传统数据库是以表为中心的，表不承载业务含义。通用 AI 小助手进不了企业的业务流程——你让它补货，它得先把 ERP 里整条供应链从头看一遍，才可能给出一个成立的答案。

他的解法是本体，四要素：**业务对象、实例、属性、关联关系**，连起来是一张业务图谱。但只到图谱还不够，还要往上叠两层：

- **规则函数**：把自然语言写的业务规则变成可执行判定。他举的例子是「年龄大于 120 判为异常，后续流程不再走」。
- **行动**：模型不能只给建议，要能真的调系统。给出「此处建议补货」，点一下按钮就真的下补货单。

他把「知识图谱」和「业务本体」分得很清楚：知识图谱是专业概念和静态知识的描述，业务本体是面向业务运行时的动态支撑体系。两者语义可以映射，但**只靠知识图谱撑不起企业智能体**。

落地节奏他也说了实话：第一个场景大约两个月，第二个一个月，之后才能批量复制。前提是**你得真懂那个行业**——他举油气钻头的预防性维护，一台设备上万个零部件、钻头几百个传感器，「不懂就没人愿意跟你聊」。

我把这套东西映射回我们公司（垂直招聘），大概是这个样子：

| 层 | 我们的对应物 | 现状 |
|---|---|---|
| 业务对象 | 职位、企业、候选人、简历、技能、行业、门店 | 散在各服务的表里，字段含义靠人记 |
| 规则 | 「薪资缺失不可投递」「同企业 90 天内不可重复投递」「资质不符不进推荐池」 | 散在 PHP 业务代码的 if 里 |
| 行动 | 投递、邀约、面试安排、推荐 | 各接口各写一套 |

断的是中间那层。规则写在代码里不是错，错在它**不是一个可编排、可解释、可回放的层**。运营想问「这个人为什么没被推荐」，只能去翻代码。

## 八、阿里云那三层，我只取两条

第二场是厂商方案，三层结构：引擎层、上下文引擎层、智能体搜索层。里面有不少数字（千亿向量多租户、P99 从 605ms 到 65ms、千亿文档检索 1.2s 到 200ms），都是讲者口径，我没有条件验证，**这里只当架构参考，不当事实引用**。

真正能拿走的是两条判断：

1. **搜索正在 API 化。** 未来的搜索可以没有界面，直接被 Agent 调用。这个趋势对做后端的人是好消息——你得把检索能力做成接口，而不是做成页面。
2. **多租户的大规模向量，靠的是路由 + 分片，不是靠堆机器。** 先定位业务空间，再在那个空间里检索，把「千亿」拆成很多个「百万」。

至于「全球第一」「改变世界的 15 个开源软件」「安全防护 100%」这类话，我在现场就过滤掉了。产品宣传和技术判断是两件事。

## 九、这一课对我最狠的一句

我们公司不是没牌。

`veryeast-go` 里已经有 `internal/pkg/elasticsearch` 包，`ve_search` 仓也在，Python 那边跑着 FAISS 和 LangChain。论基础设施，该有的都有了。

缺的是**把 ES 当语义层用，而不是当筛选器用**。

- 筛选器思维：给定条件 → 拼 DSL → 返回列表。相关性是用户自己解决的。
- 语义层思维：给定意图 → 多路召回 → 融合 → 重排 → 给出证据和理由。相关性是系统负责的。

差别不在技术栈，在**要不要为相关性负责**。这句话，是我这一下午唯一带回来的、能改我工作方式的东西。

## 十、六条工程经验，可以直接照抄

![6 条工程经验（现场幻灯片）](/images/2026-11-28-semantic-search/fig2-six-lessons.jpg)

现场最后一页是六条经验，我按「我们怎么做」补了落地动作：

1. **规则 + 词典抽取槽位。** 可控、可复现、可评测。先用规则把「城市、薪资区间、经验年限」抠出来，别指望模型一步到位。
2. **多路召回比单路调参更稳。** 单路最高 80.38%，融合后 84.10%。先把第二路接上，再谈调参。
3. **向量不是银弹。** 型号、规格、编号这类，交给 BM25 和实体召回。
4. **先做好数据清洗。** 清洗后的商品信息才做 embedding，实体抽取之后再去做精准匹配。脏数据进向量库，等于把噪音固化。
5. **融合用名次，权重进配置。** RRF 打底，权重放配置中心，线上可调。
6. **一切可回放。** 冻结配置 + 全链路轨迹。没有回放，所有优化都是猜。

## 十一、我记下的错，和我不敢信的数

现场是语音转写出的纪要，错得很有代表性，顺手记一笔当作反面教材：

- Elasticsearch 被转成「引拉设计」「隐藏设计」「UL 设计」；
- Milvus 被转成「Minors」；
- RRF 被转成「RF」，BM25 被转成「MR25」；
- BBQ 的全称被讲成「Better Battery Partition」，实际是 Better Binary Quantization。

**不采信清单**：所有「提升 N 倍」「降低到 1/N」的厂商数字、所有「全球第一」、所有无法核实的内部组件名。架构可以学，数字要自己跑。

这也是我给自己定的规矩：**听会可以带架构走，不能带数字走。**

## 十二、收尾三句话

1. 搜索没有消失，它变成了智能体的证据链——**理解、召回、核对、交付**，每一步都要有检索兜底。
2. 单路调参有天花板，**多路融合是结构解法**；融合看名次，不看分数。
3. 语义层的门槛不在模型，**在你敢不敢把业务规则写成可编排的一层**。

明年我大概率会拿这套东西在公司做一个最小的试验：一个业务域、四路召回、RRF 打底、可回放。做成了再谈第二个域。
