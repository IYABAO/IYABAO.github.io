> 本文核心数字来自一次真实的交叉复算现场（9 条判据、两套环境、一份中途落地的模拟副本、三种被分开统计的结果）。涉及的多 agent 协作体系已泛化，用「复算方」「被复算方」「某工程线 agent」代称；文中路径、账号、地址均已泛化，命令行只保留可说明问题的骨架。正文不含任何 agent 真名、内网路径或敏感数据。

## 一份报告里，三个互相矛盾的数字

那天凌晨，一份交叉复算报告同时给出了三个结论，看起来谁也不服谁：

```text
判据读数层：9/9 条逐字一致，差值全为 0
生产可运行层：7 条复算命令崩溃，核实器打出 6 条 BROKEN
跨文件视图层：4 处读数对不上，相对差都超过 5%
```

第一眼像是自相矛盾：既然 9 条读数全对，怎么会有 6 条 BROKEN？既然核实器都判 BROKEN 了，凭什么说 verdict 是 Y？

后来我把这三行读明白了——它们根本不是在同一件事上表态。第一句说的是「卡片上写的数字对不对」，第二句说的是「取数的命令还跑不跑得起来」，第三句说的是「同一指标在别的文件里是不是还挂着旧数」。三句话，三个层次，各说各的。真正致命的是第二句：**同一组命令，几个小时前还能逐条吐出读数，现在却一条都吐不出来了**。

这篇就讲这场「前半夜全绿、后半夜全崩」的事故。它的根因小到只有一行代码，但它揭示的坑很大——你精心搭的隔离沙盒，可能恰恰因为太干净，把唯一会出事的那个变量给排除掉了。

## 一、同一个仓库，两套结果

先把现场摆清楚。

有个 agent（下文叫「被复算方」）维护着一张记分卡，卡上 9 条判据，每条都配了一条「复算命令」，规矩是：谁都不许信报告里的数字，自己把命令跑一遍，拿末行的 `RESULT:` 去对卡面写的「当前值」。这轮轮到另一个 agent（下文叫「复算方」）来独立复算。

复算方在两处跑了同一批命令：

- **生产树**：被复算方平时干活的那份目录，真实快照、真实台账、真实脚本都在这儿。
- **隔离沙盒**：复算方在自己工作区镜像了一份目录结构，只放真快照，**刻意排除了所有带「模拟 / 场景」字样的副本文件**。

结果：

```text
生产树：  F1→崩 F1b→崩 F2A→崩 F2B→崩 F3_B→崩 F4→崩 F6→崩   （7 条 exit=1，无 RESULT 行）
          C1bm→活 C6W→活                                    （2 条 exit=0）
沙盒：    C1…C9 全部 exit=0，读数与卡面逐字一致                 （9 条全绿）
```

7 条崩，2 条活。活的这两条有个共同点：它们不依赖那个出问题的东西。崩的那些也有共同点：它们都要经过同一个模块。

这就是整件事的题眼——**不是判据错了，是取数的路断了**。

## 二、那个被当成真快照的模拟副本

故障的引入者是一个中途落地的文件。复算窗口内，被复算方往生产树的 `weekly/` 目录下写了一个场景推演用的副本，文件名和头部长这样：

```text
文件名：POSITIONS_2LEGS_SCENARIO_20261124.md
第 1 行：模拟口径，未成交
第 2 行：本件是台账副本，不是台账本体
第 3 行：本件任何一行都不得被读成成交事实
第 8 行：AT 2026-11-24 01:28:47
```

这份文件第一行就白纸黑字写着「模拟口径，未成交」「不得被读成成交事实」。它本来是个无害的推演草稿，问题出在被下游脚本「看见」了。

复算方后来复盘时，把这一刻称为整条链的头号分歧：**一份明确声明「不许被当成事实」的文件，恰恰被脚本当成了事实的数据源**。

## 三、故障链三层：glob、排序键、模块级 fail-fast

把代码翻出来，三层缺陷叠在一起，缺一层都不会崩成这样。

**第一层：快照发现用的是无过滤 glob。**

```python
# 快照发现：把 weekly/*/ 下所有 POSITIONS_*.md 都纳入候选
def latest_positions(base):
    cands = glob.glob(base + "/weekly/*/POSITIONS_*.md")
    return max(cands, key=snapshot_sort_key)
```

`POSITIONS_*.md` 这个模式把 `POSITIONS_2LEGS_SCENARIO_20261124.md` 一起吞了进来。没有任何「排除 SCENARIO / SIM / 模拟」的判断。

**第二层：排序键只读文件头的时间戳，不看声明。**

```python
def snapshot_sort_key(path):
    head = open(path, encoding="utf-8").read().splitlines()[:8]
    ts = re.search(r"(\d{4}-\d{2}-\d{2} \d{2}:\d{2})", "\n".join(head))
    return ts.group(1) if ts else ""
```

副本第 8 行那个 `AT 2026-11-24 01:28:47` 是全目录里最新的时间戳，于是 `max()` 稳稳地把这份模拟件选成了「最新真快照」。文件头那三行「不得读成事实」的声明，排序函数一个字都没看。

**第三层，也是最狠的一层：崩溃点写在模块顶层。**

```python
# 模块顶层语句，import 期就执行，不在任何函数体内
POSITIONS = latest_positions(BASE)
F1_SNAPSHOT_DATE = re.search(
    r"(\d{4}-\d{2}-\d{2})", os.path.basename(POSITIONS)
).group(1)   # 文件名里是 20261124（无连字符）→ 匹配不到 → .group(1) 抛 AttributeError
```

副本文件名用的是 `20261124` 而不是 `2026-11-24`，正则匹配失败，`None.group(1)` 直接抛 `AttributeError`。关键在于这几行是**模块级**的——任何 `import` 这个模块的命令，都还没来得及输出第一条 `RESULT:`，就在导入阶段死了。这就解释了为什么 7 条命令「一条数字都吐不出来」：它们不是算错了，是根本没走到算的那一步。

生产态实测（退出码在 PowerShell 里精确捕获，不用 cmd 的 `%ERRORLEVEL%`——后者在管道里是解析期展开，不可信）：

```text
>> C1   exit=1 lastRESULT=(NO RESULT LINE) | lastline=AttributeError: 'NoneType' object has no attribute 'group'
>> C1b  exit=1 lastRESULT=(NO RESULT LINE) | lastline=AttributeError: 'NoneType' object has no attribute 'group'
>> C4   exit=1 lastRESULT=(NO RESULT LINE) | lastline=AttributeError: 'NoneType' object has no attribute 'group'
>> C1bm exit=0 lastRESULT=RESULT: C1B_M = (读数与卡面一致)   ← 不读 glob 快照，仍活
>> C6W  exit=0 lastRESULT=RESULT: C6_W = (读数与卡面一致)    ← 自己读锚快照，仍活
```

## 四、为什么沙盒全绿——它把唯一的故障变量排除掉了

沙盒那 9 条全绿，不是因为沙盒里的脚本更健壮。脚本是同一份脚本，代码一个字节没改。

```text
SB>> C1   exit=0 lastline=RESULT: C1 = (读数与卡面逐字一致)
SB>> C1b  exit=0 lastline=RESULT: C1b = (读数与卡面逐字一致)
SB>> C4   exit=0 lastline=RESULT: C4 = (读数与卡面逐字一致)
...（C1…C9 九条全部 exit=0）
```

绿的原因只有一个：搭沙盒的时候，为了「干净」，只复制了真快照，**把那份模拟副本排除在外了**。于是 glob 吞不到它，排序键选中的还是真快照，正则匹配成功，模块导入顺利，9 条命令各吐各的 `RESULT:`。

这就是隔离环境最阴的陷阱：**它通过剔除「噪声」，顺手把生产里唯一会要命的那个变量也剔除了**。沙盒测的是「在理想输入下逻辑对不对」，答案是对的；生产测的是「在真实输入下链路跑不跑得起来」，答案是崩的。两个答案都是真的，但它们回答的不是同一个问题。

## 五、"逻辑对"和"链路活"是两件事

事故报告最后没有把三种结果揉成一个数，而是分开列了三行各自收口：

```text
RESULT: XCHK_CRITERIA = criteria=9/mismatch_gt5pct=0/broken=0
RESULT: XCHK_PROD = production_broken=7/root_cause=模拟副本被glob判为最新快照/verify_broken=6
RESULT: XCHK_VIEW = comparisons=4/mismatch_gt5pct=4
```

这个「不混计」的处理，是整份报告最值得抄的地方。三种数如果揉在一起，无论报大报小都会骗人：

- 只报「9/9 全对」，等于掩盖「现在谁都跑不出数」这个事实；
- 只报「6 条 BROKEN」，等于宣布「判据全废了」，可卡面数字其实一条没错；
- 把视图层的 4 处旧数算进判据层，等于拿下游没同步的锅去砸上游。

分开之后，每一层的责任人也清楚了：读数层归被复算方维护卡面，视图层归那些忘了回写旧数的文件，生产层的 BROKEN 归写 glob  Discovery 逻辑的脚本。谁的问题谁领走，不串味。

一句话概括这一节：**绿灯只能证明被测的那条路通，不能证明没被测的路也通**。沙盒是一条第 3 条变量被摘掉的路，它绿得毫无说服力。

## 六、可复算证据：怎么把一场事故钉死

这次复盘之所以站得住，靠的是每层都留了可重跑的证据，而不是靠谁的叙述。

**证据一：独立的快照选择诊断。** 不复用业务脚本，自己写几行，直接问「到底选中了谁」：

```python
picked = latest_positions(BASE)
print("PICKED", os.path.basename(picked))
print("BASENAME_DATE_MATCH", re.search(r"\d{4}-\d{2}-\d{2}", os.path.basename(picked)))
print("L97_WOULD_CRASH", re.search(r"\d{4}-\d{2}-\d{2}", os.path.basename(picked)) is None)
```

输出原文：

```text
PICKED POSITIONS_2LEGS_SCENARIO_20261124.md
BASENAME_DATE_MATCH None
L97_WOULD_CRASH True
```

三行把因果链钉死：选错了文件、文件名没日期、必崩。

**证据二：沙盒 A/B 隔离。** 同一批命令在生产树和沙盒各跑一遍，除了「有没有那份副本」以外其余条件全部相同。结果一边 7 崩 2 活、一边 9 全绿，唯一变量就是那个文件。这是标准的对照实验——把「是脚本本身有问题」和「是输入里有脏东西」这两个假设干净地分开了。

**证据三：读取时刻与落地时刻对照。** 报告特意记了一句：卡面 9 条读数的 `RESULT:` 是 01:17–01:19 跑出来的，**早于**模拟副本落地的 01:26。所以读数结论成立，不是因为它幸运，而是因为它确实采自副本出现之前。这条时间线是判断「读数对不对」和「链路后来坏没坏」的分界线——没有它，两个结论就会打架。

这三件证据合起来，把「谁对」的问题变成了工程问题，不再需要任何人拍胸脯担保。

## 七、三条修法，按性价比排序

复算方没有越权去改被复算方的脚本，只把修法分成三档交回去。这个「复算不代改」的边界也值得学。

**① 快照发现加排除规则（治本，必做）。** 根因在 glob 无过滤。文件名不含 `YYYY-MM-DD`、或路径含 `SCENARIO` / `SIM` / `_sim` 的，一律不进候选：

```python
cands = [
    p for p in glob.glob(base + "/weekly/*/POSITIONS_*.md")
    if re.search(r"\d{4}-\d{2}-\d{2}", os.path.basename(p))
       and not re.search(r"SCENARIO|SIM|_sim", p, re.I)
]
```

**② 模块级 fail-fast 改成显式报错（必做，防下次）。** 让崩溃说人话，并列出候选，别抛一个莫名其妙的 `AttributeError`：

```python
m = re.search(r"(\d{4}-\d{2}-\d{2})", os.path.basename(POSITIONS))
if not m:
    raise RuntimeError("快照文件名无日期，无法定位快照日：%s（候选：%s）"
                       % (POSITIONS, cands))
```

甚至可以从文件头的 `as-of` 取日期，彻底不依赖文件名——那样 `20261124` 这种命名就不再是雷。

**③ 把模拟副本挪出 glob 路径（治标，立竿见影）。** 放到 `weekly/_scenario/` 这种不匹配发现模式的目录，或者换成不带 `POSITIONS_*.md` 模式的文件名。治理层面这一条最快，改一个存放位置就能让生产立刻恢复。

三条建议同时做前两条、第三条兜底。只做第三条不改代码，等于把地雷挪到别处，下次换个副本名字照样炸。

## 八、一张可以抄的规矩：隔离环境要保留生产的"脏"

把这场事故压成一张规矩，以后谁搭沙盒、谁做隔离验收，照着走：

```text
1. 沙盒必须保留生产的关键变量，尤其是"脏数据"——那些声明为模拟、
   临时、副本的文件。全绿沙盒先怀疑它太干净。
2. 文件发现逻辑（glob/find）必须有显式排除规则，不能靠命名默契；
   命名默契一定会被人用另一种命名打破。
3. 崩溃点不要写在模块顶层。import 期 fail-fast 会让所有下游命令
   在输出任何结论前集体沉默，排查成本翻倍。
4. 复算结论分层写：读数层 / 链路层 / 视图层各报各的，不混计。
5. 记录每次取数的时刻，和数据落地的时刻；两个时刻的先后，
   决定"读数对不对"和"链路坏没坏"能不能同时成立。
6. 复算方只复算、不代改；修法交回原作者，边界不清就没有独立性。
```

这张纸的核心只有一句：**隔离环境的目的不是制造一个全绿的结果，而是制造一个和生产一样脏、但可控的环境**。把脏东西全擦掉的沙盒，测出来的是你希望看到的世界，不是你真正要部署的那个世界。

回到开头那三个矛盾的数字。它们其实一点都不矛盾：判据读数是对的，取数链路是断的，视图文件是旧的——三件同时为真的事，被三种口径老老实实分开记账。真正危险的从来不是「报了红」，而是把红藏进一个漂亮的平均数里，然后对着全绿的沙盒说「上线没问题」。

那天如果只看沙盒的 9 个绿勾，就会在 7 条命令全崩的生产树上，签字放行。
