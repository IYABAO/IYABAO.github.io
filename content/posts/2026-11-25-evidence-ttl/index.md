## 一、先上一组昨天刚跑出来的数

我在维护一份求职用的证据登记册：哪些公司在招什么岗位，每一条都要有可复算的抓取证据，不是「我记得」。登记册有个数字口径，11 月 22 日那次刷新读数是 **102**。11 月 25 日夜里做了一轮红线复验（零登录、零投递、全部公开页实时抓取），把账龄超线的 **35 家关键家逐家重抓**，结果：

- 能复现「登记岗位真在招」的：**17 家**；
- 续不上的：**18 家**——岗位轮换下架 11 家、needle（岗位标题锚点）未复现 3 家、抓取失败 3 家、1 家旧账黄灯维持剔除；
- 登记册读数 102 → **85**，一个晚上掉了 17。

这组数来自我自己的两份核验记录，`J1V_FRESHEN_20261126.md` §1/§3 和 `PLANB_ENTRY_20261126.md` §0，全文会不断引用它们，每条数字都标了出处，你可以逐条去对。这轮还立了三条硬纪律，直接决定上面那组数能不能信：**零登录、零投递、全部证据逐字节存档**——每家公司的原始响应（哪怕只有 89 字节）都落盘，后来者可以逐字节回溯每一家的抓取现场；抓不到的如实标「轮换下架 / 抓取失败」，零沿用旧证据充数（来源：`J1V_FRESHEN_20261126.md` 头部声明、§9 raw 留痕索引）。

先说清楚口径：掉这 17 个不是「规则收紧了」，是**现实本来就变了**——那些岗位在 11 月中旬确实真的在招，证据当时也真的成立；到了 11 月 25 日，其中一半多的岗位已经下架、轮换，或者入口页面本身变成了拿不到数据的壳。证据没撒谎，只是**过期了**。

掉数还有一笔结构账，逐格可对（来源：`J1V_FRESHEN_20261126.md` §2.2）：

```text
102 − 85 = −17 = legacy 基线 46→41（−5）+ confirmed 基线 56→44（−12）
```

掉的每一条都落了 `FRESHLINE-EXCLUDED`（超龄剔除）标记，肉眼可见、可复核；另有一类灰色样本如实挂黄灯——淘天集团是已失效（LAPSED）登记家，不进通过/不通过合计，本轮活性复核照样做了，渲染出 34,992 字节的岗位列表，标「黄灯 OK」而不借机捞回分数（来源：同文件 §3 说明③）。

这就是这篇要讲的区分：**「我查过了」是一个动词，「证据还在有效期内」是一个状态。** 两者差着一个时间戳、一个锚点、一个到期日。缺任何一样，「查过了」就只是心理安慰。

## 二、证据是耗材：48 小时就能烂，7 天只是宽限

这轮复验给证据定的有效期是 **7 天**：抓取日 2026-11-26（按「晚于 21 点的抓取记次日」的记账规则）+ 7，到期日 **2026-12-03**。到期之后这条证据自动作废，读数必须重抓刷新。

但 7 天不是「东西 7 天才变」，而是「我最多容忍 7 天没复核」。对象本身的腐烂速度比这快得多。同一轮里我有直接观察：

- 阿里控股的招聘门户，**11-24 16:08** 上架了一个新岗，**11-25 10:18** 又上架一个——不到 24 小时，列表长出新条目（来源：`PLANB_ENTRY_20261126.md` §0.3）；
- 反向也一样：11 月中旬登记的岗位，比如滴滴（11-14 抓的）、云从科技（11-17 抓的）、三一重工（11-18 抓的），重抓时门户活得好好的、岗位列表一大页，**就是找不到登记的那一个**（来源：`J1V_FRESHEN_20261126.md` §3 逐家总表）。

一边以日为单位上新，一边以日为单位下架——这就是招聘数据的半衰期，粗粒度就是 48 小时量级。所以「我 11 月中旬查过，这家公司在招」这句话，到 11 月 25 日的真实含义只是「**它曾经在招**」。拿它做今天的决策，跟拿 2024 年的股价决定今天的买卖是同一类错误。

顺带一个进阶坑：同一批事实，换口径读数就不一样。这轮掉数之后，「全池登记册」口径从 102 掉到 85，但另一条「回录判定」口径重跑前后都是 **65，纹丝不动**（来源：`J1V_FRESHEN_20261126.md` §2.1）——因为它压根不依赖抓取时效。所以引用别人（或几周前的自己）的数字时，先问三件事：什么口径、什么时候抓的、过没过期。数字本身也要带标签，不然「我查过，是 102」这句话照样害你。

## 三、反例一：HTTP 200 不是证据——假 positionId 照样返回成功页

SPA（前端渲染）招聘门户最擅长制造「我查过了」的幻觉。这轮我专门造了假证据去撞自己的判定门，原始记录在 `PLANB_ENTRY_20261126.md` §3 的负对照 NC-C，raw 文件名 `90_negctl_bogus_100034640099_20261125_223924.html`：

```text
真岗位详情页（positionId=100034640003）：HTTP 200 / 8,157 B / SSR <title> 含岗位名「阿里控股-Agent 开发工程师（数字员工）」
假岗位详情页（positionId=100034640099，末两位是我编的）：HTTP 200 / 8,079 B / 标题回落成通用官网名「阿里巴巴控股集团招聘官网」
另一家同理：假 ID 返回 HTTP 200 / 6,549 B，标题同样回落
```

看到了吗：**接口对不存在的岗位照样返回 200**，页面大小和真岗位只差一两百字节。如果你只检查「请求成没成功」，假 ID 会被当成「岗位在招」。真正能区分的只有一件事：页面内容里那个**锚点**（岗位标题）在不在。

同轮还有更极端的 200。网易的入口 raw（`01_entry_raw.bin`）抓下来只有 **89 字节**——HTTP 200，内容是空 JS 壳；百度智能云的 raw **60 字节**，渲染后满打满算 399 字节，疑似 WAF 拦截壳页；顺网科技拿到了 58,360 字节的响应，两轮浏览器渲染后依然一个岗位条目都没有（来源：`J1V_FRESHEN_20261126.md` §3 第 3、4、15 行）。三个都是 200，三个都啥也没证明。

结论很硬：**状态码、响应大小、「页面打开了」，都不是证据。证据 = 你声称的那个具体内容（needle）在原始响应里逐字命中，且 raw 存了档。**

反过来，一条「够格」的证据长什么样？本轮 Shopee 的复现包是现成样板：入口 GET 原始响应 `01_entry_raw.bin` **299,899 字节**、列表 API 原始 JSON **338,686 字节**、翻页 offset=100 再来一份 **346,148 字节**，外加互证四字段——登记岗位标题、identifier、抓取时刻、登记入口 URL——逐家在证据文件 `04_freshen_evidence.txt` 里逐字命中，由校验脚本逐家判 PASS（来源：`J1V_FRESHEN_20261126.md` §3 第 26 行、§4）。同样是 200，这一包和上面那个 89 字节的壳页，谁配当证据一目了然。

## 四、反例二：公司活着 ≠ 岗位还在——岗位轮换抓不到 needle

这是本轮掉数的最大头：11 家「轮换下架」。它们的共同剧本是——门户渲染得漂漂亮亮，真实岗位列表一大堆，唯独你登记的那条找不到了。两个有全量核对的样本（来源：`J1V_FRESHEN_20261126.md` §5）：

```text
云从科技：招聘 API 全量核对 total=97 岗、其中 79 个 open——公司确实在大量招人，但登记的那个岗位已轮换下架
有赞：门户渲染出 19 个在招岗位，逐条比对，不含登记岗
```

「我查过了，云从还在大规模招人」——所以呢？你登记的是**那个岗位**。公司在招、岗位没了，证据就是死的。这一类翻车在日常生活中极其常见：「我查过这家餐厅还开着」（开着，但你常点的那道菜下了菜单）、「这个接口还在」（在，但你依赖的字段删了）、「这门课还能选」（能选，但你冲着的那个导师不开这个方向了）。

处置纪律上，这轮定了两条相反的防线，都值得抄：

1. **续不上就掉数，不许换锚凑数。** 铁律是「不换锚」：不能因为原岗位下架了，就顺手抓个同公司新岗位顶上，把登记册读数维持住。掉就是掉，102→85 如实写。中通快递那个样本最能说明「锚」的苛刻程度——它不是没找到岗位，而是登记的 needle 里含地址占位符，本轮逐字对不上，照样判「未复现」掉数，而不是「差不多就算命中」（来源：`J1V_FRESHEN_20261126.md` §5）。
2. **抓不到也不许判死。** 那 3 家「抓取失败」明确标失败而不是标「已停招」——网易的查询接口是 POST-only（本轮纪律只 GET）、百度疑似被 WAF 挡、顺网是渲染没出数据。这是**方法问题，不是对方停招的证据**（来源：`J1V_FRESHEN_20261126.md` §10 第 3 条）。过期机制最容易滋生的歪路，就是把「我没查到」偷偷升级成「它不存在了」。

连「复现成功」的一侧也有元数据审计：极氪本轮判 fresh 复现（浏览器渲染 HTTP 200，needle「绩效经理」命中，证据文件 8,123 字节），但翻旧账时发现登记册上它的旧抓取时刻**漏更新过**，本轮把 `old_capture=2026-11-17 03:35:12` 逐字对照修正、留了裁决注记（来源：同文件 §3 第 23 行）。证据的保质期字段本身也会写错——所以它也得是可核对的，而不是手抄台账。

一句话收拢：**证据的对象是「命题」，不是「话题」。**「云从在招 Go」和「云从在招那个后端岗」是两个命题，前者今天还成立，后者已经死了。你当初查的到底是哪句话，决定这条证据什么时候作废。

## 五、反例三：旧快照穿新马甲——四条负对照全部真触发

「我查过了」最危险的形态，是拿旧证据冒充本轮结论。这轮我做了四次「栽赃测试」，故意伪造证据喂给自己的判定门，看它抓不抓得住。四条全部真触发，原文如下。

前两条来自投递入口包 `PLANB_ENTRY_20261126.md` §3，判定门要求四项齐全：本轮抓取时刻（精确到秒）、HTTP 200 或渲染有条目、具体岗位标题、岗位 ID。在招状态叫 LIVE，缺任一项降级 UNVERIFIED：

```text
NC-A 抹掉证据记录里的 fetched_at 再跑判定：
     with_ts=True without_ts=False  missing=['①本轮抓取时刻缺失'] -> 从 LIVE 降级 UNVERIFIED，触发
NC-B 把当晚 20:19 那份旧快照的时刻当「本轮抓取时刻」喂进去：
     ts=2026-11-25 20:19:00 verdict=REJECTED（早于 21:00 硬线）-> 拒收，触发
```

后两条来自登记册侧 `J1V_FRESHEN_20261126.md` §6，在沙盒里动生产登记册的副本：

```text
NC1 把华大集团的证据回拨到 11-17 的旧抓取：
     审计输出 FRESHLINE-EXCLUDED: 华大集团，读数 85 -> 84，旧证据必被检出掉数
NC2 把趣链科技的 captured_at 伪造成 2026-11-30（未来时刻）：
     FRESHNESS_GUARD 报 INVALID，退出码 1，fail-closed 整本登记册拒绝出数
```

四条测试对应四种最常见的作弊路径：没时间戳的「查过了」（NC-A）、拿历史快照当本轮结论（NC-B）、复用过期证据充数（NC1）、直接改时间（NC2）。判定门全部抓住，而且 NC2 那种「连伪造未来时间都会被闸住、闸不住就整本作废」的 fail-closed 设计，比「发现可疑就警告一下」良心得多。整套测试跑在沙盒副本上，生产登记册一字未动（raw 目录 `tmp\freshen_negctl_20261126\`）。报告里对应的原话值得整段抄走：

> 本轮没有任何一家以「沿用旧证据」方式留在分子里。旧证据文件一律保留原路径原字节，audit/recount 对续不上的家自动 FRESHLINE-EXCLUDED，肉眼可见、可复核。

还有一个不算负对照但同样防抖的手段：**双样本复现**。投递入口包那轮抓取跑了两个批次（22:36 和 23:00 起），两轮的条目集合、positionId、发布时间、详情页字节数逐项一致（`8157/8132/8191/8132/8151/8160` 与 `6620/6605` 完全相同）——单次读数可能撞运气，两次一致才敢说是稳定事实（来源：`PLANB_ENTRY_20261126.md` §0.1）。

## 六、四条可以直接抄走的规矩

把这轮踩出来的东西压成四条，按「写进证据条目的字段」的顺序讲。一个能自证的证据条目长这样：

```text
claim:    阿里控股-Agent 开发工程师（数字员工）-企业智能事业部 在招（杭州）
needle:   positionId=100034640003 + 岗位标题逐字出现在详情页 SSR 标题里
raw:      05_detailpage_100034640003_20261125_230058.json + 详情页 HTML 8,157 B（已存档）
captured: 2026-11-25 23:00:58（精确到秒）
ttl:      7 天 -> expiry 2026-12-03（对象日级轮换，7 天已是宽限）
status:   LIVE（在窗口内）/ EXPIRED（到期作废，必须重抓，禁止沿用）
```

**规矩一：每条证据带 captured_at，到点作废，作废只有一条出路——重抓。**「沿用一下应该没事吧」就是 NC1 要抓的行为。沿用旧证据的成本看似是零，实际是把「未知」伪装成「已知」混进结论。

**规矩二：TTL 按对象的半衰期定，不按你想省事的力度定。** 招聘岗日级轮换，给 7 天；行情类分钟级；而 git commit、已发布的论文这类不变对象，一次抓取永久有效。先问「这个东西多久变一次」，再定有效期，别反着来。

**规矩三：锚定内容，别锚定接口。** 判定标准写成「needle 在 raw 里逐字命中」，写成可执行的断言，而不是「打开看了，有」。能报出 needle 原文、raw 文件名、字节数的才叫查过；只能报出「我记得有」的，是印象。

**规矩四：给你的判定门跑负对照。** 拿一条明知是假的东西喂进去——抹掉时间戳、造个假 ID、回拨一次日期——看你的流程会不会接住。接不住，说明你过去所有「查过了」都在裸奔。这不用多少功夫，NC-A 到 NC2 四条全部实装在一个只读校验脚本里（`verify_planb_entry_20261126.py`、`verify_j1v_freshen_20261126.py`），一遍跑完不到一分钟。本轮的真实输出里，`NC_A_no_ts -> FIRED`、`NC_B_stale_ts -> FIRED`、`NC_C_bogus_id -> FIRED` 三行是连着打印出来的，同一个脚本还扫了自己的源码、断言自己没有引入任何网络库——校验者自证清白，也是校验的一部分（来源：`PLANB_ENTRY_20261126.md` §7 自检串）。

## 七、这套东西不只治招聘数据

换个场景立刻适用，每个都对应上面一条反例：

- **测试与 CI**：昨天的绿灯不代表今天的绿灯。测试结论必须绑 commit hash + 运行时间，不然「我们上线前测过的」就是一句 NC-B——拿旧快照穿新马甲。
- **竞品/行业调研**：截图不是现状。每张截图、每个引用数字旁边写抓取日期，报告评审时先扫一遍哪些已经出了有效期。
- **写文章/做汇报引用数据**：「我查到行业规模是 X」→ 那是哪一年的口径？对象半年一变的数据，引用时的 TTL 应该短到你不好意思用。
- **给 LLM agent 配检索工具**：这是这轮的直接经验——agent 最爱说「我查过了」，因为它的检索结果里没有「过期」概念。工具返回就该带时间戳和有效期字段，判定脚本该带负对照，否则模型会把三天前的结果当今天的现实，而且说得理直气壮。
- **日常消费与二手交易**：「我查过，那件还有货」——查的是几点几分？库存类对象的有效期的单位是分钟，不是天。同理「这家店我上周看过还开着」，一周足够让门脸换人；越易变的对象，结论的保质期越要以小时计。反过来，一次查证长期免检的对象也存在：身份证号、出生年月这类事实抓一次用十年——TTL 该由对象的变更频率决定，而不是由你查它的难易决定。

## 八、收尾：把「查过」降级成一次动作，把「有效」升级成一种状态

回到标题那组数：35 家、17 家复现、18 家掉数、有效期 2026-12-03。这轮最大的收获不是登记册数字变小了，而是整个流程从此对「查过了」这三个字免疫——**它只陈述过去某个时刻为真，对现在什么都不承诺**。

判断一条证据还值不值得信，就问三个字段：什么时候抓的（captured_at）？抓的是什么命题（needle，不是话题）？过没过期（expiry）？三问有一个答不上来，它就不是证据，是一次记忆。这条登记册的下一道闸已经写进计划：**2026-12-01 前后安排新一轮重抓**，因为所有人都知道 12-03 一到，这批证据会逐日烂掉——区别只在于你是提前重抓，还是事后才发现自己在拿尸体导航。
