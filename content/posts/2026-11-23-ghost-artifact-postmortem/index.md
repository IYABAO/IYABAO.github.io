> 说明：本文所有数字都来自一台本机上真实跑过的记录，命令附在文末可原样复跑。涉及的 agent 以 A / B / C 指代，路径已去掉个人标识，凭据、账号与任何账户金额一律不出现，涉及比例的地方只用相对数。这不是一篇谈 AI 伦理的文章——它是一次事故复盘，讲的是「已生成」这三个字怎么骗过我，以及我后来用什么笨办法把它钉死在磁盘上。

## 一、最开始，我信了它说的「已生成」

有一轮模拟面试，我让 agent 连答两轮、每题落一份稿。它每轮都回「已生成、已落盘」，路径齐全、格式漂亮。我去核对磁盘——一份都没有。

不是一次，是**连续五次**。五个「已完成」，五个幽灵产物，最后一轮交叉复算时被逐条打回。

那一刻我明白的事很简单，但很扎心：**agent 说「写完了」和磁盘上真有这个文件，之间没有任何因果关系。** 它可以在完全没有调用写盘的情况下，生成一段极其可信的「已写入」叙述。这不是它在骗我——它真诚地认为自己完成了。问题在于它把「生成了写入动作的文本」当成了完成，而我指的是「文件此刻在磁盘上、且内容是对的」。同一个词，两套定义。

后来我把这类东西起名叫**幽灵产物**：汇报里有、磁盘上没有；或者磁盘上有半个、汇报里说有全部。这篇文章就讲它是怎么被发现的，以及我加了哪四道闸。

## 二、三条「已完成」，一台磁盘，三种下场

幽灵产物最典型的现场，是三条任务几乎同时把状态推到「待验收」，口径一模一样：「已完成，产物已落盘，请验收。」

按字面收，三条都该过。但我有个笨习惯：谁说「已生成」，先看磁盘。于是三条各跑一遍 `Get-Item`：

```text
甲：汇报已完成 / 磁盘交付件真实存在 37190 B        -> 通过
乙：汇报已完成 / 磁盘报告不存在，只有 19 个临时脚本 -> 打回
丙：汇报已完成 / 磁盘 jsonl 150 行，报告与 commit 无 -> 打回
```

三条「已完成」，一条真、两条假。三种下场正好是幽灵产物的三种长相：

- **完全不存在**：报告文件名在磁盘上查无此物，目录里只有 19 个下划线开头的临时脚本。执行者把「目录里多出来一堆文件」当成了「报告生成了」——脚手架不是交付件，堆再多也堆不出报告。
- **只落一半**：数据文件写了 150 行，但报告正文和 commit 都没有。流水线跑到中间就停了，汇报却按跑完处理。
- **数字达标但内容为壳**：字节数够、文件名对，打开全是占位符。这是最贵的一种，靠文件名和大小都戳不穿。

这里要先说清楚一件事：这不是谁恶意撒谎。三个执行者都真诚地相信自己做完了，它们的汇报在各自会话里也是「真实」的——只是那个真实停留在写入的那一刻，没有延伸到此刻的磁盘。

## 三、第一道闸：字节实测，把「完成」钉在磁盘上

被咬了五次之后，我加的第一道闸很朴素：**任何声称落盘的产物，必须附一条 `Get-Item` 的实测输出，贴出字节数和时间戳。**

```powershell
powershell -NoProfile -Command "Get-Item '<产物绝对路径>' | Select-Object Name,Length,LastWriteTime"
```

规则写死：拿不出字节数的「已写入」，一律按没做处理。这条闸落地当天就抓到一次——我扫自己的心跳记录，光一个主题目录下就有 **47 个心跳文件**，日期从月初铺到月底。这个量级下，靠「它说写了」完全不可靠，你必须让每一条声称都带一个外部可核验的锚点。

但这里有个我纠结很久的边界：**字节数到底算什么？** 我一开始把它当验收标准——文件有 8000 字节就算过关。后来发现不对。同一个主题的一篇稿，写入工具回显的是 **4,537**（字符数），磁盘实测却是 **9,643 B**（字节数）——中文稿两者差一倍多，我差点把字符数当字节数上报。另一个场合，核验方磁盘实测是 **14,363 B**，而汇报里给的是 **74,459** 与 **0** 两个悬殊数字，真实值既不取大也不取小。

结论：**字节数证明不了内容对，它只证明这个东西真的存在于磁盘上。** 它是防撒谎的**下限**，不是验收的**门槛**。就像体重之于智商——体重为 0 一定有病、筛掉；但体重 70 公斤不能说明聪明。你不会用体重筛智商，但体检会先称体重，因为它最便宜、最不可能造假。把下限当门槛，会放过一堆「体重达标但内容是空壳」的产物；把门槛当下限，又会卡死本来没问题的小文件。两者不能混。

## 四、第二道闸：判据器自己也会撒谎

第一道闸解决了「文件在不在」，但很快我发现：**用来验证的工具本身也会骗人。**

我有一组复算命令，用来从表格里抽判定词、统计命中数。有两条命令长期返回 0，看起来「零命中、非常干净」。真相是命令里的正则把 Markdown 表格转义带进来的 `\|` 当成了**字面竖线字符**——在 .NET 正则里 `\|` 不是「或」，是匹配一个真的竖线。于是正则永远匹配不上，`$q` 恒为 0。这种「永久绿」比报错危险得多：它不会红，回归也发现不了，你以为判据达标，其实判据从来没被执行过。

```text
原写法: (答满\|半满\|接不住)   -> 匹配字面字符串，恒 0
按提示删反斜杠               -> 空分支交替，440/440，更糟
修后: 排除一切字面 '|'，运行时用 -join [char]124 拼竖线
```

修法不是换一个正则就完事，而是立了条规矩：**命令里禁止出现字面竖线，改完必须跑「植入探针」**——故意塞一条一定能命中的假数据进去，看判据器能不能抓到。抓不到，说明判据器坏了，不是被测对象达标。这一轮修完，逐条独立进程实测：`J2=6/10`、`J2=6/10`（连跑两次一致）、`J3=0`、`J4=0`、`J5=5`，退出码全 0；再用植入探针验证新命令能命中，各 2/2 PASS。

教训写进了纪律：**给判据器也定一个判据。** 一个从不出错的验证器，往往只是一个没在工作的验证器。

## 五、第三道闸：fence lint，把「代码有没有语言标记」变成机器可判的断言

幽灵产物的近亲是「渲染事故」：本地看着有 5 个代码块，线上只剩 4 个，静默缺一块，状态码还是 200。还有一类更隐蔽——开围栏没写语言标记，Hugo 的 PaperMod 主题会把围栏自己渲染成正文，代码块变成一坨裸文本。

这类问题靠肉眼盯不住，我把它做成了一条只读、零依赖的断言脚本。判据是实测校准过的：

```text
收围栏（裸 ```）本来就该是裸的，一律合法；
只有「开围栏且 info string 为空」才计为缺标记。
状态机：逐行匹配行首 3+ 反引号，closed->open 为开栏、open->closed 为收栏，奇偶配对。
```

它的输出是一行机器可读的 RESULT：

```text
RESULT: FENCE_LINT = 篇=1 / 开围栏=10 / 缺标记=0
```

`缺标记=0` 就是过关线。这行的价值不在于它多聪明，而在于它把「这篇文章的代码块都带语言标记了吗」这种主观判断，变成了一个退出码 0/1 的客观事实。凡是能写成退出码的，就不该再靠人去「看一眼」。

## 六、第四道闸：200 不是终点，回读才是

发布闭环上，我也踩过「commit 当完成」的坑。真正的闭环是：commit → push → 线上 URL 首次 200 → curl 实测 → 回读比对。中间每一环都可能掉链子。

**404 是常态，不是失败。** 有一篇稿子，commit 和 push 都成功，但连着四次请求线上 URL 都是 404，第五次才 200——构建部署有传播延迟，通常不到两分钟。把 404 当失败去回滚，才是真的失败。首次 200 后，我用 curl 实测拿到 **200 / 66,588 B**，并点了几个渲染指标：`goat=0 / pre=20 / h1=1`，和预期对齐。

**200 只证明发布成功，不证明内容站得住。** 有一篇稿子已经 200 上线、也过了 lint，我再通读一遍，抓出五处口径硬伤——时序倒挂、延迟夸大、日期错位、归属含混、举了不属于该类的例子。于是主动做了第二次提交订正，并且不只信状态码，而是用「新串命中 + 旧串不命中」双向反证确认线上跑的是订正版：

```text
RESULT: FRESHNESS = v2 已上线 / 异常项=0
```

针对前面说的静默缺块，我不再看整体状态码，而是对每个代码块点名探针：

```text
RESULT: RENDER_CHECK = 缺块=0 / 探针=6
```

还有一个自指的小难题：报告里要写「本报告多少字节」。直接写死一个数，一改就变。我的办法是先放一个定宽占位 `RRRRR`，全部写完、实测出精确值后等宽回填——比如 `RRRRR` → `13914`——保证回填前后总字节数 delta=0，让报告里的数字是精确值而不是「大约」。回填会推高修改时间，所以文件里记的是测量时刻、目录里显示的是落盘时刻，这两个不一样，得说清楚。

## 七、覆盖事故：同名 + 字节变小 = 出事了

最后补一道防守：不是「有没有生成」，而是「有没有把原来的东西冲掉」。

有一次，某个主题的主文件在 08:10 写成了 **7,648 B** 的完整版，08:37 又被写成 **1,759 B** 的单家片段——同一个文件名，直接覆盖，整份成果凭空消失，而且没人发现。根因不是手抖，是缺命名规矩。

从那以后定死三条：

- 过程产物文件名必须带时间后缀 `<主题>-<日期>-<时分>.md`，禁止直接改写当日主文件名；
- 任何覆盖语义的写盘之前，先查目标是否已存在、且是否比本次内容大——是，就判为潜在覆盖事故，改用带后缀的新名；
- 同一主题当天累积，优先追加而非重写；判据很硬：**字节变小 + 同名，就是覆盖事故**。

## 八、把下限焊成门槛：四条能抄的规矩

这场复盘下来，我把「已生成」这句话从幻术改成了可核验的事实，靠的是四道闸。抽象出来，就是四条能直接抄走的东西：

1. **凡声称落盘，先 `Get-Item` 报字节数和时间戳。** 拿不出实测的「已写入」，按没做处理。字节是防撒谎的下限，不是验收的门槛。
2. **给判据器也定判据。** 命令里禁字面竖线、改完跑植入探针；一个从不出错的验证器，通常只是没在工作。
3. **把主观判断写成退出码。** 围栏有没有语言标记、线上有没有缺块，都做成 `缺标记=0`、`缺块=0` 这样的断言，不靠人眼看。
4. **把 200 当起点，不当终点。** 首次 200 后还要实测字节、点渲染指标、回读标题与首段、必要时双向反证版本。Commit 不是闭环，回读才是。

回到开头那五次谎报。它们没有毁掉什么，反而逼出了一套机制。现在 agent 再说「已生成」，我不会先信，也不会因为不信就去手工重写一遍——我会让它把字节、判据、断言、回读一并贴出来。它如果真做了，这些证据唾手可得；它如果没做，就当场露馅。

这比「相信 AI」或者「不相信 AI」都更有用。工程上真正该做的，从来不是判断它这次有没有撒谎，而是让撒谎在机制上变得不可能。

# 1. 产物落盘字节实测
powershell -NoProfile -Command "Get-Item '<产物绝对路径>' | Select-Object Name,Length,LastWriteTime"

# 2. 围栏缺标记自查（0 = 过关）
py -3.12 D:\<工具区>\scripts\fence_lint.py --path <本篇>

# 3. 线上首段回读比对（避免解码假阴性，curl 落地再读）
curl --noproxy "*" -s <线上 URL> -o page.html
powershell -NoProfile -Command "$s=Get-Content page.html -Raw -Encoding utf8; [regex]::Matches($s,'<title>.*?</title>') | ForEach-Object { $_.Value }"
```
