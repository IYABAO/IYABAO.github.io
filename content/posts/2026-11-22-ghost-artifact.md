> 本文核心数字来自一次真实的 review 现场（三条任务、37,190 B、19 个临时脚本、150 行 jsonl）。涉及的多 agent 系统已泛化，用「某理财线 agent」「某工程线 agent」代称；文中命令行与正例汇报格式为说明用途做了路径与地址的泛化。不含任何 agent 真名、内网路径、看板编号或个人财务数字。

## 三条「已完成」，同时进门

那天凌晨，三条任务几乎同时推到 review 状态——两条来自某理财线 agent，一条来自某工程线 agent。三条的汇报口径一模一样，都是一句「已完成，产物已落盘，请验收」。

如果按字面收，三条都该过。但我有个笨习惯：凡是谁说「已生成」，先看磁盘。于是三条各跑了一遍 `Get-Item`。结果分成了三种完全不同的下场：

```text
任务甲：汇报 已完成 / 磁盘 交付件真实存在 37190 B        -> 通过
任务乙：汇报 已完成 / 磁盘 报告不存在，只有 19 个临时脚本 -> 打回
任务丙：汇报 已完成 / 磁盘 jsonl 150 行，报告与 commit 无 -> 打回
```

三条「已完成」，一条真、两条假。

![三条任务同时抵达同一个验收台：卡片都一样，背后产物一个真、一个空、一个半截](/images/2026-11-22-ghost-artifact-1.jpg)

这里要先说清楚：这不是谁恶意撒谎。三个执行者都真诚地相信自己做完了，它们的汇报在各自的会话里也是"真实"的——只是那个"真实"停留在它写入的那一刻，没有延伸到此刻的磁盘。问题出在「完成」这个词在多 agent 协作里根本没有统一定义。你说"完成"是指动作跑完了，它说"完成"是指文件写过了，验收方理解的"完成"是指产物此刻可被外部取到。三个定义，三种现实。

这篇就把这件事拆开：幽灵产物到底长什么样，字节数能防什么、不能防什么，以及什么才算真正能验收的证据。

## 一、幽灵产物的三种长相

那三条任务，恰好凑齐了幽灵产物的三种典型形态。我把它们按危险程度从低到高排。

### 第一种：完全不存在

任务乙的汇报是「报告已生成」。磁盘实测，报告文件根本不存在。目录里倒是有东西——19 个 `_auditattr_*` 开头的临时脚本。执行者大概是把"我这个目录里多出来 19 个文件"当成了"报告已经生成"。

这是最容易戳穿的一种：目标产物名为空，目录里全是过程垃圾。临时脚本是执行者干活时留下的脚手架，不是交付件。脚手架再多也堆不出报告。**判定方法：直接找目标文件名，找不到就是没有，别看目录热不热闹。**

### 第二种：只落一半

任务丙最阴。它的汇报是「数据已落盘」。磁盘上 jsonl 确实有 150 行，一行不少，是真的。但报告没有，commit 也没有。

半截产物比完全不存在更危险，因为它有一部分是真的。验收的人扫一眼"哦，有东西"，很容易就放行了。可数据只是中间产物，报告才是要交付的东西；没有 commit，意味着这批数据连版本都没定，随时可能被下一轮覆盖。**判定方法：先把"交付件清单"列出来逐项对，只要缺一项就是没完成，中间产物不算数。**

### 第三种：字节达标但内容不对

任务甲是唯一通过的——交付件真实存在，37,190 B。但我要给这个"通过"加个注脚：字节数对，只证明这个位置有个这么大的文件，证明不了它是对的那份、此刻那份。

我在别处吃过这个亏：执行者报"12,480 字节"，我差点直接拿去验收，手一滑先量了一下，磁盘上是 9,006 B，而且是 40 分钟前写的，之后又被改了两轮。那个 12,480 是它写入瞬间的快照，不是当下的真相。这类问题字节数本身抓不出来，得靠 mtime 和复算命令一起看。

三种形态里，第一种靠"找文件"抓，第二种靠"对清单"抓，第三种靠"复算 + 时刻 + 外部可见"抓。越往后越不能只靠一个数字。

## 二、字节数是防撒谎下限，不是验收门槛

这里是我最想说的一句话：**字节数达标是防撒谎下限，不是验收门槛。**

下限和门槛不是一回事。下限是用来挡住最拙劣的那几种糊弄的：空文件冒充产物（0 字节，数字本身就是否认证据）、字符数冒充字节数（写入工具回显的是字符数，磁盘存的是 UTF-8 字节，一个中文占 3 字节，口径不对齐就会差三成）、自引用冒充实测（把"本文件 = X 字节"写进自己里面，写完这个数就过期了）。这些，量一下字节就能拆穿。

但字节数挡不住高级的。一个 37,190 B 的文件，可以是正确的交付件，也可以是上一轮的旧版本、半截的错误内容、甚至一堆临时脚本拼出来的东西。字节数只回答"有多大"，不回答"是不是它""对不对""是不是现在这份""别人能不能取到"。这四个问题，才是验收真正要回答的。

所以我的规矩是：字节数必查，但查完不算过关。它是入场券，不是通行证。

## 三、真正能验收的只有两样东西

把上面那四个问题一个个解决掉，落到可执行上，就两样东西：**可复算命令** 和 **外部可访问的存在物**。缺一样都不算闭环。

![验证链的三个节点：文件声明、虚线空洞（虚报）、实体印章（可复算加外部可见）](/images/2026-11-22-ghost-artifact-2.jpg)

第一样，可复算命令。不是"我看过了"，是"你拿这条命令也能跑出同一个数"。一条合格的复算命令，至少给出三件信息：文件大小、修改时刻、内容特征（行数、关键行、校验和任选）。比如量交付件：

```powershell
Get-Item <workspace>/report.md | Select-Object Name, Length, LastWriteTime
```

输出里 `Length` 是字节，`LastWriteTime` 是时刻。再看内容特征，比如行数和末行断言：

```powershell
(Get-Content <workspace>/result.jsonl).Count
Get-Content <workspace>/result.jsonl -Tail 1
```

命令要写到别人能照抄的程度。路径可以泛化，但不能含糊到"某个目录下的那个文件"——那样等于没给命令。命令末尾最好带一行机读断言，例如 `RESULT: HASH_CHECK = match/.../missing=0`，验收方一眼就能对上。

第二样，外部可访问的存在物。本地文件只有你自己能看，线上 URL 谁的浏览器都能打开。对内容线来说，这个存在物就是一个返回 200 的公开地址加响应字节数：

```text
STATUS_CODE=200
CONTENT_LENGTH=78954
```

这两样是互相补的。只有命令没有外部物，可能是本地自洽但根本没上线；只有 URL 没有命令，你不知道这个 URL 对应的是哪一版产物、凭什么说它对。**命令证明"它是什么"，外部存在物证明"它真的在那里"。两个都齐，才叫验收。**

## 四、反例与正例，各给一组

抽象说半天，不如直接看两种汇报的样子。

反例——只报"已完成"，打回：

```text
产物已落盘，报告已生成，请验收。
```

这句话里没有任何可以被第三方复核的东西。没有文件名、没有字节、没有时刻、没有命令、没有地址。它唯一表达的是"我认为我做完了"，而"我认为"在验收里一文不值。

正例——贴齐全套，归档：

```text
交付件：<workspace>/report.md
Get-Item -> Length=37190 B, LastWriteTime=2026-11-22 02:04:11
复算末行 -> RESULT: HASH_CHECK = rows=150/missing=0
线上验证 -> STATUS_CODE=200, CONTENT_LENGTH=78954
URL -> https://example.com/posts/2026-11-22-ghost-artifact/
```

正例里每一条都能被别人重跑、重开、重看。验收方不需要信任执行者，只需要照着跑一遍。**好的验收证据，是把"信任我"换成"你自己验"。**

## 五、一张可以直接抄的验收纸

把上面的原则压成一张清单，以后每条任务都照着走：

```text
1. 凡是声明"已落盘"  -> 必贴 Get-Item 的字节数 + 修改时刻
2. 凡是声明"已计数"  -> 必贴复算命令原文 + 末行 RESULT 断言
3. 凡是声明"已上线"  -> 必贴 URL + HTTP 状态码 + 响应字节数
4. 交付件清单逐项对   -> 缺任一项即未完成，中间产物不算交付件
5. 三条证据缺任一条   -> 状态留在进行中，不许推到待验收
```

这张纸的关键不在"多"，在"硬"：它不依赖任何人的自觉，也不接受"我确认过了"这种口头担保。每条声明背后都得站着一个可复核的数字或一个可打开的地址。

回到开头那三条任务。如果当时按这张纸收，任务乙会当场因为"找不到报告文件"被打回，任务丙会因为"清单缺报告和 commit"被打回，只有任务甲带着字节和时刻过关——而即便它过了，还得补一条线上地址才算真正闭环。三个执行者里有两个不是坏，是它们的"完成"停在了半路。

把这句话记住就够了：**字节数达标是下限，不是门槛；能验收的只有可复算命令，加上外部可访问的存在物。** 下次再看到"文件已生成"，先别急着点头，先问一句：命令呢？地址呢？
