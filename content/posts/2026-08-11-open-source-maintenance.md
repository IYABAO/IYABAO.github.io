# 开源项目维护：从 README 到 Issue 治理

写开源项目时最大的幻觉：**"代码写好了，放 GitHub 就会有人用。"** 现实：没有维护的仓库是"数字坟墓"——README 是空的、Issue 没人回、一年不更新。这篇文章是开源维护的完整清单：从"放上去"到"有人用"。

## 一、门面工程：README 是 80% 的印象

用户 10 秒决定"用不用你的项目"——这 10 秒里他只看 README。

### README 结构（10 秒看完）

```markdown
# fluxio-mcp

给 LLM 的可编程网络信息读取器（MCP Server）

**一行话定位** + **谁该用** + **效果图**

## ✨ 特性
- 批量抓取（并发）
- 网页转 Markdown
- 结构化输出（LLM 友好）

## 🚀 快速开始（10 秒跑起来）
pip install ...
fluxio-mcp --config ...

## 📚 文档链接
## 🤝 贡献指南
## 📄 License
```

### README 的关键

```
✅ 第一屏说清"这是什么、解决什么问题"（有人只看第一屏）
✅ 快速开始要"能直接复制粘贴跑通"（30 秒内看到效果）
✅ 有效果图（README 有图 vs 没图，star 差一个量级）
✅ 说清"边界"（不做什么，省得一堆 not-a-bug 的 Issue）
```

## 二、Issue 治理

### Issue 模板（省掉 50% 的沟通成本）

```markdown
## 环境
- 版本：
- OS：
- Python/Node 版本：

## 问题描述
（复现步骤 / 期望 / 实际）

## 日志/报错
```

### 处理策略

```
✅ 24h 内首次回复（哪怕只是"收到，我周末看"）
✅ 打标签：bug / feature / question / duplicate
✅ 贴"最小复现"指南（让报 bug 的人给信息）
✅ 关闭策略明确：
   - 重复 → 关闭 + 链接到已有
   - 信息不足 → 请求补充，7 天无回复关闭
   - 超出范围 → 礼貌关闭 + 说明
❌ 不回复的 Issue 会积累成"这个项目没人管"的信号
```

## 三、PR 流程

### 贡献指南（CONTRIBUTING.md）

```markdown
# 开发流程
1. fork + clone
2. 新建分支：feature/xxx
3. 改代码 + 加测试
4. 本地跑测试：pytest -q
5. 提 PR，描述：改了什么/为什么/测试结果
```

### 合并规范

```
✅ CI 必须过（测试 + lint）才合
✅ 要求"带测试的改动"（没测试的 PR 要解释）
✅ Code Review 友好：小 PR（<300 行）好合
✅ 用 Conventional Commits（feat/fix/docs），自动生成 CHANGELOG
```

## 四、Release 节奏

```
✅ 语义化版本：0.x（不稳定）→ 1.0（稳定 API）→ 2.0（破坏性变更）
✅ Release Notes：每次发布写"新增/修复/破坏性变更"
✅ 发布到包管理器（PyPI/npm）——不发布 = 用户要 clone 源码
✅ 安全修复快速出补丁版本
```

**节奏感很重要**：**每月一个小版本**，用户看到"项目活着"。

## 五、社区运营（轻量但有效）

```
✅ 至少 2 个真实使用示例（用户照抄就能用）
✅ 收集"用在了哪"（Awesome 列表收录、用户项目链接）
✅ 常见问题 FAQ（减少重复 Issue）
✅ 版本里程碑：明确"下个版本做什么"
❌ 别建一堆群（维护精力分散），用 GitHub Discussions
```

## 六、维护者的心态建设

```
真实情况：
  - star 涨得慢是常态（不是失败）
  - 大多数 Issue 是重复的（不是你的错）
  - 你不可能满足所有人（定义清晰边界）

原则：
  - 项目是你的，你有权决定方向（别人提需求不代表你要做）
  - 拒绝要礼貌但要明确（"超出范围"比"先记着"好）
  - 维护的可持续性 > 功能的丰富度（burnout 是最常见的弃坑原因）
```

## 七、避坑清单

```
✅ README 第一屏说清定位
✅ Issue 24h 内回复（哪怕只是告知已读）
✅ CI 是门面（测试红 = 项目死）
✅ 月度小版本节奏
✅ CONTRIBUTING 写好贡献流程
❌ 别开 10 个分支又不合（代码烂在分支里）
❌ 别让 Issue 堆积（每周清一次）
❌ 别吞破坏性变更不说明（升 2.0 要写明 migration）
```

## 总结

开源维护的核心认知：

1. **README 是 80% 的印象**：第一屏说清定位，快速开始 30 秒跑通
2. **Issue 治理 = 信任建设**：24h 回复、清晰标签、明确关闭策略
3. **PR 有规范**：CI 必过、测试必带、小 PR 好合
4. **节奏感**：月度版本，用户看到"项目活着"
5. **可持续 > 丰富**：定义边界，别 burnout

**开源项目的价值不是代码，是"活着的信号"**：持续更新、及时响应、清晰治理——这些比任何炫技代码都更能赢得信任。
