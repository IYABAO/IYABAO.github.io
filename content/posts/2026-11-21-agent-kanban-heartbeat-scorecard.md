> 本文写的机制来自我自己的一套本地运维目录，命令、字段、退出码均为真实结构。agent 名、判据对象、路径、端口、身份信息均已泛化为「甲/乙/丙 agent」「J1–J5」「`<workdir>`」等抽象记号，正文不含任何真实财务数据、机构名称或个人身份信息。

## 一、问题：三个 agent，没有一个能靠人盯

我手上跑了三个 agent worker，各管一摊：甲管理财线，乙管求职线，丙管工程线。它们共用一个后端框架，各有一个独立会话和自己的工作目录。

一开始我以为难点是 prompt 写得好不好。跑了几周才发现完全不是——prompt 再聪明，只要「下一步做什么」还得我来指派，三个 agent 就退化成三个聊天窗口：我不开口，它们就静止。

真正的瓶颈是三件事：

1. **谁决定现在该干什么**——不能每次都等我下指令；
2. **活记在哪**——聊天里说过的话不算数，滚出上下文就丢；
3. **怎么证明干成了**——「我觉得推进了」不是证据，得有一个能复跑、能算出数字的东西。

这三件事的答案，分别就是心跳 cron、看板、记分卡。它们不是三个功能，是一个闭环的三个齿轮。

## 二、齿轮一：心跳 cron，到点自己醒

每个 agent 有自己的定时配置文件 `<workdir>/jobs.json`，里面是一组 cron job。最基础的一条是早间启动：

```json
{
  "name": "DailyRoutine 早间启动",
  "enabled": true,
  "schedule": { "cron": "50 7 * * *", "timezone": "Asia/Shanghai", "type": "cron" },
  "task_type": "agent",
  "dispatch": { "channel": "console", "type": "channel" },
  "runtime": { "tool_safety": false, "timeout_seconds": 600 }
}
```

关键点在 `task_type: "agent"`——到点不是发一条通知给我，而是**直接唤醒一轮 agent 会话**，让它自己跑一段逻辑。定时任务在这里的角色不是「提醒器」，是「启动器」。

除了早间启动，还有更高频的心跳。心跳相位对齐到半小时一格：分钟数小于 `:47` 归到整点后 17 分（`HH:17`），大于等于 `:47` 归到 `HH:47`。一个心跳轮次醒来后只做固定的几步，写死在 agent 的行为准则里，不临场发挥：

```text
第 1 步：读差距表 <workdir>/conclusions/SCORECARD_TODO.md
        → 按「差距」列从大到小排序，挑最大的那条
        → 自己创建一条 todo，产物路径写进描述
第 2 步：精确时间的活挂 cron，可浮动的活合并进心跳清单
```

这套机制的主语是 agent 自己：自己读表、自己挑活、自己建卡。人不在环里。

为了防止三个 agent 半夜互相踩，还有几条硬约束：

- **领活锁**：同一条判据主题 2 小时内不重复领。锁窗按相位算，2 小时 = 连续 4 格。
- **睡眠边界**：22:00 之后的心跳只回填数值、刷新差距表，不领新活；23:00 由专门的 agent 统一负责提醒，其他人不重复发。
- **WIP 上限**：看板同时在做的活最多 3 件，第 4 件来了先把最不重要的退回待办池。

## 三、齿轮二：一个看板，所有活只走这一条通道

三个 agent 各自有会话，但**任务通道只有一个**：一个纯文件的看板，由三份 Markdown 组成。

```text
<workdir>/tasks/active.md     # 正在做，WIP ≤ 3
<workdir>/tasks/backlog.md    # 待办池
<workdir>/tasks/done.md       # 已完成 + 证据
```

为什么用文件而不是数据库或在线看板？因为 agent 的工具链里，读写文件是最稳、最可复跑的动作；而且文件在磁盘上，agent 会话重置后状态还在。原则是「一切落盘」：聊天里说过但没写进文件的，视为没发生过。

看板上每条任务有强制模板，其中最重要的一栏是**验收标准**——写死「什么证据算完成」：

```markdown
### N. 任务标题（起算日 YYYY-MM-DD）
- agent 已做：1) ... 2) ... 3) ...（带产物绝对路径与字节数）
- 还差本人：≤5 分钟的一个具体动作
- 验收标准：产物实测 N B（>阈值）；自检表 N 条全部有判定
- 提醒义务：每周期提一次，不许静默
```

这里有个反直觉的设计：任务状态不写「待本人」，而写「**agent 已做 X，还差本人 5 分钟做 Y**」。这是被现实逼出来的——早期任务全挂在「等本人」上，连续几周零推进，因为 agent 把「等本人」当成了终点。改成「把活做到不能再做，只留一个最小的人工动作」后，卡点才真正暴露出来。

逾期任务也不许不了了之，必须三选一，且每种都要写理由：

```text
续做   → 写清重启条件
推迟   → 写原因 + 到期重启点（如「投递季 2027.2」）
放弃   → 写理由
```

## 四、齿轮三：记分卡，每条目标都得能被一条命令算出数字

这是整个系统里我认为最有价值的一条纪律：**任何一个目标，必须能被一条命令算出一个确定的数字**。不能是「差不多」「感觉推进了」，必须是 `RESULT:` 后跟一个可复跑的数值。

我有一张主记分卡 `<workdir>/jobs/SCORECARD.md`，里面是五条判据 J1–J5。每条判据写死三样东西：当前值、目标值、差距。差距表 `<workdir>/conclusions/SCORECARD_TODO.md` 是给心跳读的活文件——注意是「活文件」，每轮心跳都可能更新，不是一次性报告。

差距表每一行的字段：

```text
判据 | 当前值 | 目标 | 差距 | 上次领取时间 | 复算方 | 备注
```

几条同样是被坑出来的规矩：

- **当前值逐位抄自主记分卡**，不许估算。找不到的项写「缺失（原因）」，不许填一个「看起来合理」的数。
- **差距写成可计算形式**。状态型判据写「`0（已达成 …）`」，不参与排序领活。
- **只领差距 > 0 的行**。差距为 0 的只记账；被裁定为 N/A 或结构性不可达的，永久排除出领活队列——否则心跳会把它当成缺口反复领，永远补不上。

判据表因为越写越长，后来按判据族拆成三个文件，主路径保留成一个短索引。拆分的唯一判据是：行数守恒、逐条可抽查。原则是「宁可多一层导航，不可丢一行原文」。

这条纪律带来的最大好处是：**进展和自欺一眼可分**。差距表读数 vs 实跑命令输出对不上，以实跑为准回写，并在备注写明分歧来源和日期。谁先写的、谁职位高，都不算数——命令输出算数。

## 五、交叉复算：算的人不能自己证明自己对

如果数值由原作者自己算、自己写、自己宣布达标，那和没算一样。所以我给复算定了个固定环：

```text
甲 agent 算的 → 乙 agent 复核
乙 agent 算的 → 丙 agent 复核
丙 agent 算的 → 甲 agent 复核
```

固定映射写进差距表的「复算方」列，原作者不许自算自证。落地分两种情况：

- **复算方不是我**：只回填、只登记，不自证。
- **复算方是我**：我在看板上给原作者建一条以「复算：」开头的任务，描述里带三件套——被复算产物的绝对路径、要跑的复算命令原文、期望的 `RESULT:` 落点文件。不等人派活。

别人的复算任务优先级高于自己新挑的差距项：WIP 顶到上限时，把自己挑的那条退回待办池，不许把别人的复算卡住。复算值与卡面不一致，仍然以实跑命令为准回写，分歧来源写进备注。

这套「谁算谁复核」的环，本质上是在三个 agent 之间引入互相制约——每个数字背后至少两个人看过，一个人算、另一个人证。

## 六、两件容易忽略的事

**第一，交付前的四项自检是硬门槛。** 任务推到「待验收」之前，必须逐条真跑并把原始输出贴出来，没有例外：

```text
a 产物落盘   → 报字节数 + 修改时间，来自文件系统的真实查询
b 复算       → 原样跑任务给的命令，贴 RESULT 行原文
c 脚本自检   → 本轮改过的脚本，当场跑最小用例，确认退出码 0
d 内容线自检 → 代码块围栏检查 + 线上 URL 取状态码
```

任一项没过就留在「进行中」，不许进验收。谎报「已写入」「已上线」却拿不出字节数和时间戳，一律按没做处理——这是被反复打回之后立的规矩。

**第二，代码块必须带语言标记。** 我们线上的静态站构建器对无标记的围栏有特殊渲染：会把裸围栏当成图床语法渲染掉，读者看到整块代码消失。所以写完必须跑一遍围栏检查器，缺标记必须为 0：

```bash
python <scripts>/fence_lint.py --path <posts>/2026-11-21-agent-kanban-heartbeat-scorecard.md
# RESULT: FENCE_LINT = 篇=1 / 开围栏=N / 缺标记=0
```

它的判据很克制：收围栏本来就应该是裸的，一律合法；只有「开围栏但 info string 为空」才算缺标记。一个状态机逐行配对，奇偶归属，简单但每次上线前都得过。

## 七、三个齿轮怎么咬合

把它们串起来看，闭环是这样转的：

```text
心跳 cron 到点醒来
   ↓ 读差距表，挑差距最大的一条，自己建卡
看板 active.md（WIP ≤ 3，每条带验收标准）
   ↓ agent 把活做到只剩一个最小人工动作，产物落盘
记分卡 SCORECARD.md（每条目标一条命令算数字）
   ↓ 差距表刷新；复算方按固定环独立复核
数值一致 → 收口；不一致 → 以实跑为准回写 + 记分歧
   ↓ 下一轮心跳读到新的差距表，再挑一条
```

三个 agent 各跑这套环，唯一共享的是「通道只有一个、数字说了算」这两条纪律。

回头看，让 agent 真正自驱的从来不是更强的模型或更巧的 prompt，而是把「下一步做什么」「做完算数吗」「谁来证伪」这三个问题，各自交给一个不依赖人、可复跑的机制。心跳解决第一个，看板解决第二个，记分卡加交叉复算解决第三个。

模型会换，prompt 会改，但这三个齿轮一旦咬合，换谁的 agent 都能接着转。
