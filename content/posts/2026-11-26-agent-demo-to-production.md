## 一、先说结论：两种能力，市场已经分开定价

过去两年聊 Agent，大部分场景还停在「搭一个能跑的 Demo」：接上大模型、拼几个工具调用、跑通一条 happy path。但真正在生产环境跑过一段时间之后会发现，Demo 跑通只是入门，**让它稳定地每天可用，是另一门手艺**。

公开招聘口径里，这个区分已经被写进岗位要求和薪酬区间：

- 2026 年 1—7 月，新经济行业新发 AI 岗位数量同比增长 **790%**，平均月薪 **63,160 元**；其中 AI 应用开发岗位占比 **60.97%**，Agent 开发工程师是应用类里最热门的岗位方向（来源：财新转脉脉行业报告，2026-09-17，[caixin.com](https://www.caixin.com/2026-09-17/102486024.html)）。
- 明确要求「Agent 稳定性工程」的岗位，薪酬中位数高出 **34%**，招聘周期 **47 天**（AI 岗位平均 **29 天**）；企业级 Agent 项目常见卡点被归为三类：任务流分支设计不合理、状态管理混乱、缺少可观测性。报告把「会搭 Demo」和「能让 Agent 稳定线上工作」直接定义成两种能力（来源：京报网转 Skillver 研究，2026-08-06，[bjd.com.cn](https://news.bjd.com.cn/2026/08/06/11903646.shtml)）。
- 另一份对 200 多份 2026 校招 JD 的社区归纳显示，LangChain 在约 **34.3%** 的 Agent 岗位描述中出现，LangGraph 加 MCP 被视为生产环境标配，约 **89%** 的团队在做可观测性建设（来源：牛客社区校招口径，[nowcoder.com](https://m.nowcoder.com/discuss/879082734507810816)；社区样本与社招资深岗有别，只作方向参考，不作结论依据）。

需求增量在 AI 应用与 Agent，而真正有溢价的部分，是把 Demo 变成可靠系统的那一段工程。下面是我自己在一套多 Agent 体系里踩过的四类缺口，以及它们分别对应稳定性工程的哪一块。

## 二、调度缺口：最危险的故障是「不报错，只是少了一行」

第一类缺口发生在调度层。给 Agent 配了定时心跳之后，最容易假设「定时器到点就会跑」。实际跑起来才发现，有一种故障不抛异常、不告警，只是日志里少了一行记录。

我遇到过一次：心跳脚本里负责把时间归到时段标签的判断写错了，两个触发时刻落进了同一个时段。结果第二个触发每小时都被幂等锁拦下，静默不写日志。表面看定时器配置没动、进程也在跑，实际上每小时丢了一跳。

归段逻辑的正确形态是：相位 `a,b` 对应「早于 b 归 a，否则归 b」，让两跳分别落在不同时段；写成把两跳并成一段的判断，不会触发任何报错，产能却被无声砍掉一半。这类问题只能靠对照两个独立数据源（定时任务流水的分钟众数、日志行首分钟分布）交叉验证，单看其中一个都发现不了。

对应到稳定性工程，这一块补的是**任务流分支与调度可靠性**：每个触发槽位有没有走到、分支条件会不会把第二跳吞掉、被锁拦下的那次算不算一次有效心跳，都要有明确口径，而不是默认「进程活着就等于调度正常」。

## 三、产物可信度缺口：自报的「已写入」不能作为验收依据

第二类缺口是最容易被忽略的：Agent 自己汇报「已生成、已归档、已写入」，这句话本身不可信。验收只认两处——磁盘上实测到的文件字节数与修改时间，以及接口返回的状态码。

几个实测过的坑：

- 写文件工具返回的回执是**字符数**，不是字节数。中文按 UTF-8 编码一个汉字占三字节，字符数和字节数可能差出两倍多，拿回执当字节数核对会得出错误结论。
- 一条任务的汇报正文是空的，不等于什么都没做。中途产出目录里可能已经落了十几份探测文件，只是最后一份正式台账没改、汇报没写。只看汇报文本会把半成品误判成幽灵产物，反过来也会把半成品当成完成。
- 汇报里写的文件名，和磁盘上的真实文件名可能差一个连字符；汇报里给的路径，也可能和实际落盘的子目录错位。按汇报路径点查不到，要再扫一遍目录比对文件名，不能直接判「磁盘无此文件」。

所以验收时我把交付物分成三种形态分开处理：**幽灵**是什么都没留，需要重做全套；**半成品**是做了前半段、缺后半段，打回时点明「已做 X、只需补 Y」；**瑕疵**是内容对、只是编号或格式错，只改指定一处，别的不许动。形态判断靠磁盘证据，不靠汇报措辞。

这一块对应的是**状态管理与产物可追溯**：每一份产物落在哪、属于哪条任务、当前是否有效，要有可回查的位置；结论层和过程层分开，一主题一份当前有效结论，带日期的快照只留作过程记录。

## 四、复算缺口：自己算的不算数，段绿也不等于全绿

第三类缺口是判据自我证明。一条目标判据如果只由执行方自己复算、自己打分，等于没有验收。

落地做法是交叉复算：每家的判据由另一家独立跑一遍，复算结果和卡面自评不一致就单列分歧，写明谁对、为什么。独立复跑抓出过两类问题：一是卡面填的当前值，和复算命令真实输出对不上；二是判据命令只统计「段名有没有出现」，段内已经失败也算命中，段数增加了，掩盖的问题也跟着增加。

这里还有一个容易自欺的口径：一段巡检命令 `exit 0`，不等于这一段没有 FAIL。我见过把「段命令跑通」当成「段全绿」的写法，复算器即使有失败项也返回成功，于是真正的红项被洗成了「全绿」。验证这种口径不能只看正常运行，要注入一个明确失败的负对照，确认它在失败时确实报红、退出码非零；造不出反例的「全绿」，只是装饰。

对应到可观测性建设，这一块要求系统能区分「命令可执行」和「结论成立」：稳定量（脚本里写了几段）和浮动量（当天有几段通过）不能塞进同一格判据；失败必须能被看见，一段只会报通过的检查，加多少段都不产生价值。

## 五、降级缺口：不可达就如实标注，不许写成「无讨论」

第四类缺口是对外信息采集。探测一个外部渠道拿不到结果，最容易写成「该渠道无讨论」。这是把「我没采到」偷换成「那边没有」，两种事实完全不同。

实测边界：有的社区通道经常返回不可达，这时候记录应当是「渠道不可达」，而不是「没有相关声音」；招聘平台公开 JD 样本依赖岗位公开发布，只作区间信号，不等于本人能拿到的水平；社区归纳和社招资深岗位存在样本偏差，引用时要连同来源类型一并标注。

降级容错的原则是：某个数据源失败，该分区标「不可用」，整页不崩；采不到的缺口留空待补，不为了好看补数字；超时一类的操作默认 fail-closed，不把超时当成放行。涉及不可逆的对外动作（下单、投递、发布、代登录），只备料，执行权留给本人。

## 六、稳定性工程补的四块，对照清单

把上面四类缺口对齐到公开报告里的卡点，稳定性工程主要在补四块：

| 缺口类别 | 补的能力 | 可机械判定的检查口径 |
|---|---|---|
| 调度分支 | 任务流分支设计、触发槽位覆盖 | 两个独立数据源交叉核对触发时刻；被锁拦下的跳有明确有效性口径 |
| 产物状态 | 状态管理、产物可追溯 | 验收以磁盘字节数与修改时间为准；结论层与过程层分离 |
| 可观测性 | 失败可见、复算独立 | 交叉复算单列分歧；负对照注入后必须报红；稳定量与浮动量分格 |
| 降级容错 | 不可达如实标注、失败不崩 | 采不到记「不可达」不写「无讨论」；超时 fail-closed；不可逆动作只备料 |

## 七、边界与不做项

- 本文引用的招聘与岗位数据来自公开平台、行业报告与社区归纳，存在样本偏差；区间信号不等于本人可拿到的 offer 水平，也不构成投递或下单建议。
- 不堆框架名词：框架只是工具，真正区分 Demo 与生产的是闭环、状态、观测与降级，而不是用了哪个编排库。
- 社区校招口径与社招资深岗位有别，文中已单独标注，不作为资深岗位判断依据。

## 八、一条今天就能用的规则

如果手上有一个 Agent 刚跑通，别急着加新功能。先问四个问题：每一次触发是不是真的执行了、每份产物落在哪能不能回查、结论有没有第二家独立复算过、注入一个失败时它会不会真的报红。这四问答不上来，Demo 再流畅，离稳定上线也还有一段距离。
