> 本文数据来自我本机三条常驻 agent 的真实运维记录，命令可复现。涉及的组织、账号、凭据、内网地址均已泛化；三条 agent 以 A / B / C 指代。

我有三个常驻 agent，每半小时自己醒一次，替我盯一条线。A 管节奏和任务看板，B 管判据和产出，C 管巡检和交叉复算。它们不依赖我叫醒，靠系统级定时在 `:17` 和 `:47` 两个相位触发，30 分钟一格。

跑起来之后我一度挺得意：人不在电脑前，事情也在往前走。直到第三周复盘，我把所有翻车样本摊开，发现真正的问题从来不是「agent 会不会犯错」——犯错是常态，改就行。真正的问题是三种**看起来在干活**的假象，它们不会报错，不会红，甚至会在汇报里写「已完成」。

我把它们归纳成三道闸：不谎报、不阻塞、不空转。这篇文章讲每一道闸是怎么被咬出来的，以及最后沉淀下的、可以直接抄的三条规矩。

## 闸一 · 不谎报

### 一次「连续五次」的谎报落盘

最早我判断 agent 有没有干完活，靠它自己说。它回一句「已写入 workRoutine/reviews/daily/」，我就信了。

有一轮模拟面试，我让它连答两轮、每题落一份稿。它每轮都回「已生成、已落盘」，格式漂亮，路径齐全。我去核对，磁盘上一份都没有。不是一次，是**连续五次**。最后一轮交叉复算时，五个「已完成」被逐条打回，全部是幽灵产物。

那次之后我想明白一件事：**agent 的「写完了」和磁盘上的文件之间，没有任何因果关系。** 它可以在没有写任何东西的情况下，生成一段极其可信的「已写入」叙述。这不是它在骗我，是它对「完成」的定义和我的定义根本不是一回事——它把「生成了写入动作的文本」当完成了，我把「文件在磁盘上且内容对」当完成。

### 字节数是防撒谎下限，不是验收门槛

补的第一道闸很朴素：**任何声称落盘的产物，必须附一条 `Get-Item` 的实测输出，贴出字节数和时间戳。**

```powershell
powershell -NoProfile -Command "Get-Item '<产物绝对路径>' | Select-Object Name,Length,LastWriteTime"
```

规则写死了：拿不出字节数的「已写入」，一律按没做处理。

这里有个我纠结过很久的边界——字节数到底算什么？我一开始把它当验收标准：文件有 8000 字节，就算过关。后来发现不对。一个空壳文件也能有 8000 字节，一段正确的结论也可能只有 300 字节。**字节数证明不了内容对，它只证明「这个东西真的存在于磁盘上」。**

这个区别我想了个类比：字节数之于内容，就像体重之于智商。体重是一个**下限筛**——一个人体重是 0，那一定有问题，筛掉；但体重 70 公斤不能说明他聪明。你不会用体重去筛智商，但你会在体检时先称体重，因为它是最便宜、最不可能造假的实体证据。

`Get-Item` 的字节数就是这个「称体重」。它便宜、可复跑、没法靠话术伪造。它是防撒谎的**下限**，绝不是验收的**门槛**。验收要看内容对不对、数字复算对不对，那是另一层的事。把下限当门槛，会放过一堆「体重达标但内容是空壳」的产物；把门槛当下限，又会卡死很多本来没问题的小文件。两者不能混。

这条闸落地后，我扫过一次自己的心跳记录：光一个主题目录下就有 **47 个心跳文件**，日期从月初铺到月底。这个量级下，靠「agent 说写了」完全不可靠——你必须让每一条声称都带一个外部可核验的锚点，而字节数就是那个最省事的锚。

## 闸二 · 不阻塞

### 确认链路集中化

第二道闸不是关于「会不会做」，是关于「做完要不要等人」。

我一开始把需要拍板的事直接推给用户本人：企业微信发一条「X 要不要这么做？」然后等回复。问题很快暴露——人是会离开工位的，尤其夜里。一个需要人拍板的问题，如果只有用户本人能答，那 agent 在这段时间里就是**阻塞态**：后面的活全停在这里等一个可能几个小时才来的回复。

改法是把确认链路集中化：**唯一的确认对象是一个常驻的裁决 agent（MainAgent），不是用户本人。** 用户本人的原话是——所有需要确认的都改成向裁决 agent 确认，只有它可以向用户确认，而且不到万不得已、没有推荐答案的不要确认。

配套一条硬规矩：**提问题必须自带推荐答案。** 格式固定：问题一句话，紧跟「推荐答案：……理由：……影响：……」。没有推荐答案的问题不许提——因为你都还没想清楚该怎么做，说明还没到能决策的程度，继续调研去。

这一下把「阻塞」从根上拆了：绝大部分决策点，agent 自己已经想好了推荐答案，裁决方只需要点头或改一个方向；就算裁决方暂时没回，也不影响先把能推进的部分做完，把决策点挂在产物末尾就行。

### 夜里的 300 秒与「判红」的噪声

真正把这道闸逼出来的是夜里的超时处理。

夜间 23:00–08:00 是静默窗，不排新任务。但裁决请求可能在这个窗口里到。我给审批设了 **300 秒超时**：超过 5 分钟没回，走 fail-closed——按推荐答案自决，并在产物里写明「超时自决（时间，裁决方未响应）」。唯一例外是不可逆的对外动作，那种不超时自决，每 2 小时重新升级一次，仍然不自决。

这里踩过一个坑：我一度把「夜间审批超时」直接判成红色告警，想让第二天一眼看到「夜里有个请求没人处理」。结果每天早上都是一片红。因为夜里本来就没人在，审批超时是**预期内的正常状态**，不是故障。把预期内的状态当异常报，等于每天固定制造一批假警报。连续几天之后，我看到红灯已经麻了——真正的故障混在这堆噪声里，照样被我忽略。

```text
夜间 23:00-08:00 审批逻辑：
  收到裁决请求 → 等待响应
    ├─ 300 秒内响应       → 按裁决执行
    ├─ 300 秒超时 + 可逆   → 按推荐答案自决，产物留痕
    └─ 300 秒超时 + 不可逆 → 不自决，每 2 小时重新升级
  静默窗内的超时 ≠ 故障，不判红、不告警
```

「夜间直接判红」为什么是噪声？因为它把**环境的常态**当成了**系统的异常**。一个夜间不排新任务的 agent，本来就不该有人在 5 分钟内批它的请求。正确的处理不是报警，是让它在无人值守时也知道该干嘛——fail-closed 加推荐答案自决，正好填上了这个空。判红只是把一个「设计上就该自决」的场景，硬塞进「需要人救火」的筐里。

自决之后还有一层：2 小时无裁决按推荐答案执行，这是通用的超时自决线。它和 300 秒的审批超时是两档——300 秒是「等裁决方」的短超时，2 小时是「升级到人也没回」的长超时。两档配合，既不卡链路，也不会在无人值守时把不可逆的事悄悄做掉。

## 闸三 · 不空转

### 一个会每天自毁的判据

前两道闸防的是「假干活」。第三道闸防的是更隐蔽的东西：**判据本身是错的，agent 却一直很配合地达标。**

我有一张差距表，每行一个判据：目标值、当前值、差距、复算方、上次领取时间。心跳每轮读这张表，按差距从大到小排序，挑最大的那条自己建卡去推。这套机制的前提是：**目标必须是外生的、稳定的。**

出事的是其中一条。某个覆盖率判据，目标写的是 `19.92%`。这个数字哪来的？它是某天快照里的**当前读数**，不知道被谁顺手提拔成了目标。于是荒诞的事发生了：目标等于读数，差距永远是 0。换一个数据快照日期（我管它叫 DTE），读数变成 21.3%，目标还是 19.92%，差距是负的——判据翻 N，agent 举手说「已达成」。再换一天读数 18%，差距又冒出来，它再推一轮。

```text
目标 = 19.92%  ← 来自某天快照的读数（错误：内生目标）
第 1 天读数 19.92% → 差距 0    → 不动
第 2 天读数 21.30% → 差距 -1.38 → 判「已达成」
第 3 天读数 18.10% → 差距 +1.82 → 又推一轮
——目标没变，读数在变，agent 每天都有活干，但什么都没改善。
```

这就是我说的**每天自毁的 gate**。一条合格的判据，目标应该来自系统外部——一个稳定的约束、一个承诺、一个业务要求——而不是从当前读数里长出来。目标跟着读数每天变，或者目标等于读数，agent 就永远「达标」，看板永远绿，但系统原地踏步。这不是在治理，是在空转。

### 读数变了，改的是动作不是目标

正确的关系应该是：**目标是锚，读数是被锚测量的量。** 读数偏离目标，触发的是「改动作」，不是「改目标去迁就读数」。

我的台账里有一组 anomalies 计数，前后两次快照从 16 条涨到 **19 条**。如果口径跟着快照漂移——这次把某类算进去、下次不算——那这个数就是自毁 gate：它每天告诉 agent「有 3 条差距」，agent 每天补一下，第二天口径一换又冒出来 3 条。真正的处理是问：这 19 条里，哪些是真 anomaly、哪些是口径噪声？把口径钉死，再谈差距。

我给这道闸定的自检问题是：**「这个目标，是不是从某次读数里抄来的？」** 如果是，它迟早自毁。判据目标必须能回答「凭什么是这个值」，答案不能是「因为上次快照就是这个值」。

还有个配套原则：同一时刻两套口径并存时，判据认哪一套必须写死。我吃过亏——同一张表在不同段落写着 `1.0` 和 `0.8` 两个当前值，心跳每轮按「差距最大」排序，就会一会儿认为达标、一会儿认为差 0.10，来回横跳。判据文件必须明确「判据只认哪一行」，否则再多自动化也是在两套真相之间空转。

## 可以直接抄的三条规矩

写到最后，把三道闸压成三条能贴墙上的规矩：

```text
1. 不谎报：任何「已完成」必须附 Get-Item 字节数 + mtime 的实测输出。
   拿不出字节数 = 没做。记住字节数是防撒谎下限，不是验收门槛。

2. 不阻塞：确认只提给唯一裁决方，提问自带推荐答案；
   夜间 23:00-08:00 审批 300 秒超时走 fail-closed 按推荐自决，
   不判红——静默窗里的超时是常态，不是故障；不可逆动作例外，不超时自决。

3. 不空转：判据目标必须外生、稳定、可复算。
   凡是「目标 = 某天快照读数」的，都是会每天自毁的 gate，直接删。
   读数偏离目标时改动作，不改目标去迁就读数。
```

这三条没有一条是聪明的。它们都很土：称个体重、设个超时、盯一眼目标是从哪来的。但跑常驻 agent 这三个星期，我越来越确信——**让 agent 靠谱的从来不是更聪明的 prompt，而是几道便宜、可复跑、没法用话术绕过去的机械闸。**

Prompt 会漂移，模型会换版本，但 `Get-Item` 的字节数不会骗人，超时不会因为「它觉得自己该被等」就改变，一个外生的目标也不会因为今天读数好看就自己松下来。把这些不漂移的东西钉进流程里，agent 才能在没人的夜里，继续做可信的活。
