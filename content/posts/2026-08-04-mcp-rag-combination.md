# MCP 与 RAG 结合：Tool 即知识的边界

RAG 的局限：知识是"静态快照"（索引时定了，之后不变）。MCP 的强项：能力是"动态接入"（随时调用）。把两者结合——**把知识变成工具**，让 LLM "查询即检索"——是知识型 Agent 的新架构。

## 一、RAG 的天花板

```
传统 RAG：
  离线建索引 → 查询时检索 → 拼上下文 → LLM 回答

问题：
  1. 知识更新要重建索引（招聘数据每时每刻在变）
  2. 检索粒度固定（只能按 chunk 检索，不能"动态聚合"）
  3. 知识被"摊平"（丢失了结构化关系：候选人→经历→项目）
  4. 权限难做（索引是全局的，过滤在检索后）
```

**核心问题**：RAG 把知识变成了"静态切片"，而业务知识是**动态、结构化、有权限的**。

## 二、MCP 给出的答案：查询即检索

```
把"检索"本身变成工具：

LLM 需要候选人信息时 → 调用 search_resume(query) 工具
  → 工具内部：ES 检索 + 权限过滤 + 结构化返回
  → LLM 拿到的是"结构化结果"，不是"文档切片"

RAG 变体：
  知识 → MCP Tool → LLM 按需查询
```

**变化**：

```
传统 RAG：知识在上下文里（塞进去）
MCP-RAG：知识在工具里（查出来）
```

**优势**：

```
✅ 实时：工具查询的是实时数据，不是快照
✅ 结构化：返回 JSON，保留关系（候选人→技能→项目）
✅ 权限：工具层过滤（比索引后过滤安全）
✅ 精准：LLM 自己决定"查什么、查几次"（按需检索）
```

## 三、架构模式

```
┌─ LLM
│   ├─ 判断需要什么知识
│   ├─ 调用对应 MCP Tool（携带查询意图）
│   └─ 基于工具结果组织回答
│
└─ MCP Server（知识型）
     ├─ 数据查询工具（search_resume / get_detail）
     ├─ 聚合工具（按维度统计：技能分布、薪资分布）
     └─ 关联工具（候选人 → 投递 → 面试记录）
```

### 模式 A：查询工具（替代 RAG 检索）

```python
@mcp.tool()
def search_resume(query: str, limit: int = 10):
    """按技能/经历/职位关键词检索候选人，返回结构化结果"""
    hits = es.search(query, size=limit, filters=perm_filter())
    return [normalize(h) for h in hits]    # 结构化，不是 chunk
```

### 模式 B：聚合工具（RAG 做不到的）

```python
@mcp.tool()
def skill_distribution(city: str):
    """统计某城市候选人技能分布（招聘分析场景）"""
    return es.aggregate(terms="skills", filter={"city": city})
```

**RAG 拿不到"聚合结果"**（chunk 检索只有文档）；MCP 工具可以返回任何计算产物。

### 模式 C：混合（RAG 兜底 + 工具优先）

```
LLM 需要知识：
  1. 优先查工具（结构化、实时、有权限）
  2. 工具没有的 → 传统 RAG 检索（文档库）
  3. 都查不到 → 明确说"不知道"
```

## 四、什么时候用哪种

| 知识类型 | 方案 |
|---|---|
| 静态文档（手册、论文） | 传统 RAG（索引成本低） |
| 实时业务数据（简历、订单） | **MCP 工具查询** |
| 结构化统计（聚合分析） | MCP 工具 |
| 混合知识库 | 混合（工具优先 + RAG 兜底） |

**判断标准**：

```
数据"会变"吗？→ 会变：工具查询（实时）
数据"结构化"吗？→ 是：工具返回结构化结果
数据"有权限"吗？→ 有：工具层过滤
以上都是 NO → 传统 RAG 足够
```

## 五、最佳东方实践

```
场景：招聘平台 Agent 需要"候选人画像"知识

方案对比：
  RAG 方案：简历文档 → 切片 → 向量索引 → 检索 → 拼上下文
    ❌ 简历是结构化的（技能/经历/薪资分开），切片会切碎
    ❌ 简历实时更新，索引滞后
    ❌ 权限：简历是敏感数据，检索后过滤风险高

  MCP 方案：search_resume 工具 → 实时查询 + 权限过滤 + 结构化返回
    ✅ 实时、结构化、带权限
    ✅ 意图响应准确率提升 50%+（上线数据）
```

## 六、避坑清单

```
✅ 工具返回"结构化结果"（别返回原始文档，LLM 消费不了）
✅ 工具描述写清"查什么、返回什么"（LLM 才能选对）
✅ 权限必须在工具层（不是上层过滤）
✅ 查询频率控制（LLM 可能反复查 → 工具级限流 + 缓存）
✅ 结果裁剪（一次返回 Top N + 关键字段，别全量）
```

## 七、MCP-RAG 的局限

```
❌ 不适合"语义模糊检索"（工具是精确查询，模糊场景用向量）
❌ 增加 LLM 推理负担（每次要"想"调哪个工具）
❌ 工具返回质量依赖上游（ES 质量差，工具结果也差）
→ 最佳实践：工具查询（精确）+ 向量检索（模糊）双通道
```

## 总结

MCP 与 RAG 结合的核心认知：

1. **RAG 的局限是"静态切片"，MCP 的答案是"动态查询"**
2. **查询即检索**：知识变成工具，实时、结构化、带权限
3. **工具优先 + RAG 兜底**：精确查工具、模糊查向量
4. **判断标准**：数据会变/结构化/有权限 → 用工具；静态文档 → 用 RAG

**2026 年知识型 Agent 的方向：不是"塞更多知识"，是"给模型更好的查询能力"。** MCP 把知识的边界从"上下文"扩展到了"整个系统"。
