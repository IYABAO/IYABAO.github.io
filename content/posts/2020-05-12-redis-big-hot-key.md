# Redis 大 Key 与热 Key：治理实战

线上 Redis 的两大杀手：**大 Key**（单个 key 值巨大）和**热 Key**（单个 key 被疯狂访问）。一个阻塞集群，一个打爆节点。这篇文章是两次事故后的完整治理方案。

## 一、大 Key：阻塞的元凶

### 问题

```
一个 key 存了 500MB 的列表（比如全量用户 ID）
→ 每次操作这 key：网络传输 500MB、内存拷贝、阻塞其他命令
→ Redis 是单线程，一个慢命令 = 全库卡顿
→ 超时、雪崩、集群故障
```

**本质**：Redis 单线程模型下，**慢命令的代价由全库承担**。

### 发现

```bash
# 1. 用 SCAN 找大 key（生产安全，不阻塞）
redis-cli --bigkeys --scan --pattern '*'

# 2. 按类型排查
redis-cli --bigkeys

# 3. 监控慢命令
redis-cli slowlog get 20
```

### 治理

```
1. 拆分：
   大列表 → 按时间/用户 ID 分桶（user:2026:01 / user:2026:02）
   大 hash → 按业务域拆分（各域独立 key）

2. 限长：
   列表限长（保留最近 N 条，LPOP 清理）
   hash 限字段数

3. 压缩/迁移：
   大 value → 压缩存储或迁出（如 JSON 存文件，Redis 存引用）

4. 禁止操作：
   KEYS *、SMEMBERS 全量、SORT 大数据集 → 用 SCAN/分批
```

## 二、热 Key：打爆单节点的元凶

### 问题

```
一个 key 每秒 10 万次读（比如爆款商品、热点新闻）
→ 单节点 CPU 打满（即使集群有 10 个节点，这个 key 固定在一个节点）
→ 其他请求全部排队 → 集群假死
```

**本质**：Redis 集群按 key 分布，**热 key 的访问无法分片**。

### 发现

```
1. 监控：节点 CPU 不均衡（一个节点 90%，其他 10%）
2. 访问统计：Redis 4.0+ 用 LFU 策略 + OBJECT FREQ
3. 代理层统计：客户端 SDK 侧统计 key 访问频次
```

### 治理

```
1. 本地缓存（最高效）：
   热 key 加一层应用本地缓存（Caffeine/进程 map）
   命中率 90%+ → Redis 压力降一个量级

2. 热 key 复制（打散）：
   hot_key → hot_key#1 ~ #N（复制 N 份，随机读）
   写入时写 N 份（写放大，只适合读多写少）

3. 降级：
   热 key 数据可容忍延迟 → 降级为"缓存快照"（每分钟刷新一次）
   
4. 限流：
   对热 key 的写操作限流，防止"缓存击穿"叠加
```

## 三、两个事故复盘

### 事故 1：大 Key 引发的全库阻塞

```
现象：线上 Redis 间歇性卡顿，P99 飙到 3s
定位：slowlog 发现 SINTER 操作耗时 8s
根因：用户标签集合存了 200 万会员 ID 的单个 key，每天全量计算交集
修复：标签按业务域拆分 + 限长 + 计算改为分批
效果：慢命令消失，P99 回到 5ms
```

### 事故 2：热 Key 打爆节点

```
现象：活动开始后 Redis 单节点 CPU 100%，集群整体超时
定位：节点 CPU 严重不均衡
根因：活动商品库存 key 每秒 8 万次读
修复：应用本地缓存（1s TTL）+ 库存 key 分片
效果：Redis 读 QPS 从 8 万降到 3000，节点 CPU 回 30%
```

## 四、预防体系

```
✅ 上线前：key 设计评审（预估 size/访问量）
✅ 巡检：--bigkeys 每周跑一次，大 key 告警
✅ 监控：节点 CPU 均衡度、慢命令、内存趋势
✅ 规范：禁止 KEYS/全量操作，列表/集合限长
✅ 应急预案：热 key 本地缓存开关、降级开关
```

## 五、避坑清单

```
✅ 大 key 排查用 SCAN（KEYS 会雪上加霜）
✅ 热 key 优先本地缓存（简单高效），再考虑复制分片
✅ 热 key 分片要注意写放大（写多读少别用）
✅ 治理后必须回归压测（验证阻塞消失）
```

## 总结

大 Key 与热 Key 的核心认知：

1. **大 Key 阻塞全局**：Redis 单线程，慢命令=全库卡顿
2. **热 Key 无法分片**：集群也救不了单个 key 的访问热点
3. **治理三板斧**：拆分（大 key）、本地缓存（热 key）、降级兜底
4. **预防 > 救火**：key 设计评审 + 巡检 + 监控

**Redis 的性能杀手从来不是"数据量大"，是"单个 key 的极端情况"。** 把大 key 拆掉、热 key 挡住，Redis 才能稳定扛住业务。
