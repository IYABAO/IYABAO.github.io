# 多级缓存架构：本地、Redis 与数据库的分工

"加了 Redis 还是慢"——因为热数据不该只走 Redis，**最快的是进程内缓存**。多级缓存架构：本地缓存扛热数据、Redis 扛共享数据、数据库兜底。这篇文章是分级设计、一致性和踩坑记录。

## 一、为什么需要多级

```
单层 Redis 的瓶颈：
  1. 网络开销：每次读都要走网络（0.1-0.5ms）
  2. 热 key 打爆单节点（前文讲过的热 key 问题）
  3. Redis 挂了全挂（没有降级）

本地缓存（进程内）：
  读耗 ~0.01ms（比 Redis 快 10-50 倍）
  不占网络、不打 Redis
  天然扛住热 key（每个进程都有一份）
```

## 二、三级架构

```
请求
  │
  ├─ 第 1 级：本地缓存（进程内，Caffeine/map）
  │    命中率 60-80%（热数据）
  │    未命中 ↓
  ├─ 第 2 级：Redis（共享缓存）
  │    命中率 +15%（次热数据）
  │    未命中 ↓
  └─ 第 3 级：数据库（兜底）
      查库 → 回填 Redis → 回填本地
```

```go
func GetUser(id int64) *User {
    // L1：本地缓存
    if u, ok := localCache.Get(id); ok {
        return u.(*User)
    }
    // L2：Redis
    val, err := redis.Get(ctx, key(id))
    if err == nil && val != "" {
        u := unmarshal(val)
        localCache.Set(id, u, 1*time.Second)   // 回填 L1（短 TTL）
        return u
    }
    // L3：数据库
    u, err := db.FindUser(id)
    if err == nil {
        redis.Set(ctx, key(id), marshal(u), 10*time.Minute)  // 回填 L2
        localCache.Set(id, u, 1*time.Second)                 // 回填 L1
    }
    return u
}
```

## 三、各级 TTL 设计（关键）

```
原则：越靠近用户，TTL 越短（一致性损失越小）

本地缓存：1s（短 TTL——更新快，容忍秒级不一致）
Redis：10min（共享缓存，更新频率决定）
数据库：无 TTL（真身）

为什么本地缓存 TTL 要短：
  本地缓存没有失效通知（进程间不通）
  TTL 越长 → 更新后读到旧数据越久
  1s TTL：最多 1 秒旧数据，可接受
```

## 四、一致性处理

```
写操作：
  先更新 DB → 删 Redis → （本地缓存靠短 TTL 自然过期）

问题：DB 更新成功，Redis 删除失败 → Redis 有旧数据
方案：
  1. 延迟双删：删 Redis → 等 500ms → 再删一次
  2. 版本号：缓存带版本，DB 版本更高 → 不读
  3. 订阅 binlog 删缓存（可靠，架构重）

实践：延迟双删 + Redis TTL 兜底（最坏多活几分钟旧数据）
```

## 五、缓存穿透防护

多级缓存下穿透更可怕（每一级都 miss 才到 DB）：

```
穿透场景：查询不存在的 ID → 每级都 miss → 直接打 DB
防护：
  1. 缓存空值（不存在的也缓存，TTL 短 30s）
  2. 布隆过滤器（不存在的直接拒绝）
  3. 接口层校验（非法参数直接返回）
```

## 六、效果数据

```
场景：简历详情读（读多写少）
  无缓存：DB 5ms，高峰期 DB 压力大
  单层 Redis：0.3ms，Redis QPS 高
  多级缓存：本地命中 0.01ms，Redis QPS 降 70%+
    L1 命中率 65% / L2 命中率 25% / DB 只扛 10%
```

## 七、踩坑记录

1. **本地缓存无限涨**：每个进程缓存一堆 key → OOM → 本地缓存必须限容量（LRU）+ 短 TTL
2. **本地缓存和 Redis 不一致**：进程 A 更新了，进程 B 本地还是旧的 → 短 TTL 兜底（可接受的秒级不一致）
3. **穿透没防护**：恶意查询不存在的 key → DB 被打 → 空值缓存 + 布隆过滤器
4. **回填风暴**：缓存全过期，所有请求同时查 DB → 回填加锁（singleflight，只让一个请求查库）

```go
// 回填防击穿：singleflight（一个 key 同时只查一次库）
var g singleflight.Group
u, err, _ := g.Do(key, func() (any, error) {
    return db.FindUser(id)   // 只有一个请求查库，其他等待
})
```

## 八、什么时候用多级

```
✅ 读多写少的核心数据（用户信息、商品、配置）
✅ 接口延迟敏感（< 5ms 要求）
✅ 有热 key 风险
❌ 写多读少（缓存命中率低，没意义）
❌ 数据一致性要求极高（秒级不能容忍）——考虑其他方案
```

## 总结

多级缓存的核心认知：

1. **三级分工**：本地（最快/最短 TTL）/ Redis（共享）/ DB（兜底）
2. **TTL 越近越短**：秒级不一致可接受，换来性能
3. **一致性用延迟双删 + TTL 兜底**
4. **穿透/击穿防护必做**：空值缓存 + singleflight

**多级缓存是"用一致性换性能"的经典权衡**：理解每一级的作用和代价，设计才有底气——不是"缓存越多越好"，是"每一级都各司其职"。
