## 开头：97 条「已生成」，我只信磁盘

上周五下午，我做了件本来该早做的事：把三个常驻 agent 当天汇报的「已生成产物」逐条量了一遍字节。不是抽查，是 97 条全覆盖。

起因是一次差点发生的误判。有个 agent 在汇报里写「产物已落盘，12,480 字节」，我差点直接拿这个数去验收。手一滑先 `Get-Item` 了一下——磁盘上是 9,006 字节，而且文件是 40 分钟前写的，之后 agents 又改了两轮。那个 12,480 是它写入那一刻的快照，不是此刻的真相。差了三千多字节，方向还是「汇报比磁盘大」。那次我要是信了，验收结论就建在空中楼阁上。

从那以后我定了个笨规矩：**agent 说生成了什么，一律不算数；磁盘上说有，才算有。** 于是有了这次 97 条全量对账。

跑完那条命令，输出的汇总行是这样的：

```text
DVD: entries=97 exact=79 larger=18 shrink=0 missing=0 remap=2 malformed=0
BYTES-EXIT: 0 (OK)
```

一眼看过去，97 条里 79 条精确、18 条磁盘更大、没有缩水、没有缺失，2 条路径做了重映射。表面是个「全绿」的结果。但正是这张看似干净的表，藏着三个我踩过的坑。这篇就讲三件事：字节数能防什么、不能防什么；幽灵产物到底长什么样；以及怎么用一条命令把 97 条声明核完。

## 一、字节数是「防撒谎下限」，不是验收门槛

先说一个容易被误解的点。这次对账里 `exact=79`，看着很安心——79 条声明的字节数和磁盘分毫不差。但我从不把「字节对上」当成「产物合格」。

原因很简单：**字节数只能证明文件的大小对，证明不了内容对。** 它是个下限——能帮你挡住最拙劣的几种撒谎，但挡不住高级的。

字节数能防的是这三类：

1. **空文件冒充产物。** agent 说写了一份报告，磁盘上 0 字节。数字 0 本身就是最响亮的否认证据——空文件里不会有内容。这类我抓到过一次，一份被引用为「存在乱码证据」的文件，实测 0 字节，证据当场作废。
2. **字符数冒充字节数。** 写入工具回显的常常是字符数，磁盘存的是 UTF-8 字节数，一个中文占 3 字节。有篇两万字长文，工具报 7,562，磁盘实测 20,271——差了近三成，方向永远是「汇报偏小」。这不是 agent 故意撒谎，是口径没对齐。
3. **自引用冒充实测。** agent 把「本文件 = X 字节」写进自己里面，写完这个数就过期了——再补一行勘误，字节又变。自引用是移动靶，永远追不上。

这三类，字节数都能抓出来，所以叫「防撒谎下限」——低于这条线，一定有问题。

但它防不住的是：**一个字节数完全正确、内容却驴唇不对马嘴的文件。** 你写一份「对账报告」，字节数 12,480，和声明分毫不差，但里面全是复制粘贴的模板话。对账工具会说 exact，验收却该打回。字节数回答的是「有多大」，不是「对不对」。把下限当门槛，等于用体重计判断一个人是不是健康——体重正常不代表没病。

所以我的用法一直是：**字节数用来证伪，不用来证实。** 对得上，只说明「没在大小上撒谎」，仅此而已；要验收内容，得另开判据。这次 79 条 exact，我的结论也只是「79 条没在大小上撒谎」，不是「79 条合格」。

## 二、幽灵产物长什么样

再说「幽灵产物」——声称已生成、磁盘却找不到。这次 `missing=0`，一个都没有。但正因为这次没有，更值得说说它长什么样，否则下次撞上还是认不出。

幽灵产物有三种典型长相，我按隐蔽程度从低到高排：

**第一种：明目张胆的 missing。** 声明里白纸黑字写着路径和字节数，对账脚本调 `os.path.getsize`，返回 FileNotFoundError。这类最好认——数上是 `missing=1`，摆在汇总行里，想忽略都难。它通常是这么来的：agent 写了文件，后来又改名或删了，声明还留在日志里；或者声明里那个路径从一开始就是 agent「打算写」的，压根没落盘。

**第二种：被路径重映射遮住的「准幽灵」。** 这是这次 `remap=2` 那两条。声明里的路径和实际落盘路径对不上——文件确实在，但被挪了位置，或者声明里的路径带了个已经废弃的目录前缀。对账脚本不会直接判 missing，而是先尝试重映射：把废弃前缀替换掉、把会话串归一，再看文件在不在。这次 2 条都重映射成功，找到了文件，所以算 remap 不算 missing。

这条最阴。如果脚本不做重映射，这 2 条会直接掉进 missing，看板上就多了两个「幽灵」。它们的真实身份是「路径漂移」——产物没丢，只是搬家没留新地址。所以 remap 和 missing 就隔一层纸：**重映射能救回来的，是路径问题；救不回来的，才是真幽灵。** 我的处理是让脚本把它俩分开报，不要把 remap 悄悄算进 exact，否则「路径漂移」这个问题就被掩盖了。

**第三种：字节数对、但文件是旧的。** 这条严格说不算幽灵，但后果一样坑。声明说「新报告已生成，8,432 字节」，磁盘上真有个 8,432 字节的文件——那是三小时前生成的旧版，新的那次写入其实失败了。对账工具看字节、看存在，全过。只有加上 mtime（LastWriteTime）才能识破：文件时间对不上这次声明的时间。所以我现在的对账，除了字节，一定带 `LastWriteTime` 一起看。

一句总结：**幽灵产物不是「文件凭空消失」，更多时候是「声明和磁盘对不上」的几种错位之一——路径错了、搬家了、时间旧了、或者压根没写。字节数只是其中一维，单看它抓不全。**

## 三、一条命令核完 97 条

第三件事，说说这条命令本身。它做的事不复杂，但设计上有几个点值得记。

```powershell
python scripts\declared-vs-disk.py --root "<workspace>" --source both --json
```

`--source both` 是指同时读两个来源：心跳日志里的「产物=路径(字节)」行，和索引文件里的声明行。为什么要 both？因为 agent 声明产物的地方不止一处——有时写进心跳，有时补进索引，有时两边都写（同一文件被声明两次，就是 repeated declaration，这正是数字会「随声明次数涨」的原因）。只读一个来源，会漏。

脚本的核心逻辑，一句话能说完（下面是泛化后的伪代码，不是原文件名）：

```python
for decl in declarations:                # 逐条声明
    path = remap(decl.path)              # 先做路径重映射
    if not os.path.exists(path):
        classify("missing")              # 重映射后仍找不到 → 幽灵
        continue
    actual = os.path.getsize(path)
    if actual == decl.bytes:
        classify("exact")
    elif actual > decl.bytes:
        classify("larger")               # 声明后又写了 → 合法追加
    else:
        classify("shrink")               # 实际变小 → 覆盖嫌疑
```

四个主分类，对应四个含义：

- `exact`：声明字节 == 磁盘字节。
- `larger`（脚本里叫 disk_larger）：磁盘比声明大。这次 18 条全是这类。原因几乎都是「声明记的是写盘那一刻的大小，文件后来又被追加了」——尤其心跳日志、索引这类 append-only 文件，每分钟都在长。它不是错误，是声明滞后。
- `shrink`：磁盘比声明小。这类要警惕，可能是文件被截断或覆盖。这次 0 条。
- `missing`：重映射后还找不到。这次 0 条。

加上 `remap`（路径被改写后才对上）和 `malformed`（声明格式本身写坏了，解析不了），就是完整的六类。

为什么 `--json`？因为这条命令是给机器看的，输出要能直接进对账台账，不给人肉读。人读的那份另有一行人类可读的汇总（就是开头那两行）。

`BYTES-EXIT` 是退出码：`shrink` 或 `missing` 大于 0 就非 0，让上游心跳或流水线能自动拦截。这次是 0，所以对账判「绿」——但注意，这个「绿」只在「大小维度」成立，跟内容验收无关，回到第一节那句话。

这里还有个我特意保留的设计：**脚本按「声明行」计数，不按「文件」计数。** 97 是声明行数，不是 97 个不同文件。同一个文件被心跳和索引各声明一次，就算 2 条。这个口径看着别扭，但不能改——因为声明本来就可能重复，重复本身是要观察的信号。真正的产物数得去重后另算，两个数并排放，谁也别冒充谁。（这个单位坑我专门写过一篇，这里不展开。）

## 四、那 18 条 larger，到底算不算事

把 18 条 larger 逐条拆开看过，结论是：一条都不用修。

它们几乎全是 append-only 文件——心跳日志、索引、台账——声明记的是某一轮的快照字节，而文件在声明之后又被追加了。比如某个心跳日志，在 04:18、04:48、05:18 各被声明一次，每次记的是当时的大小；磁盘上是最新值，自然比前几次声明都大。于是同一文件贡献多条 larger。

判断它是不是事故，盯两个不变量就够：

1. `shrink=0`：没有任何文件被写小，说明没有截断或覆盖。
2. `missing=0`：没有任何声明落空，说明没有幽灵产物。

只要这两条是 0，larger 就是「声明滞后」的健康信号，不是「文件损坏」。反过来，如果哪天 shrink 冒出来哪怕 1 条——哪怕只小 4 字节——我都会停下查，因为「变小」在 append-only 的世界里不该发生。

这也是我给这条命令的定位：**它是防撒谎的下限检查器，不是内容验收器。** 它回答「声明和磁盘在大小维度对不对得上」，回答不了「内容对不对」。两个问题，两套判据，别混。

## 五、三条带走的规矩

这篇不长，规矩也不多，三条：

1. **字节数只用来证伪。** 对不上必有鬼；对上了只说明没在大小上撒谎，别当成合格。验收内容要另开判据，而且判据要能抓「字节对但内容错」的情况。
2. **幽灵产物分四诊：路径错、搬了家、时间旧、没写。** 字节只是其中一维，配上路径重映射和 mtime 才抓得全。remap 和 missing 分开报，别让前者掩盖后者。
3. **对账按声明行计数，去重数并排放。** 97 是声明行数不是文件数；larger 多数是合法追加，盯死 shrink 和 missing 两个不变量就够。退出码只管大小维度，不管内容。

最后回到那次差点误判。12,480 对 9,006，差的不只是三千字节，是「agent 的嘴」和「磁盘的手」之间的距离。多 agent 系统里，这个距离会一直存在——agent 会抄工具回显、会写过期自引用、会声明了没落盘。你消灭不了它，只能放一把尺子在中间：**每一条「已生成」，都过一遍磁盘实测。** 97 条，一条命令，几秒钟。这点成本，换一个不撒谎的看板，值。
