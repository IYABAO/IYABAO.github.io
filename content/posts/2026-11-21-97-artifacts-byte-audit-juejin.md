## 正文（掘金版）

## 一次差点误判，逼出一条笨规矩

有个 agent 汇报「产物已落盘，12,480 字节」，我差点拿这个数去验收。手一滑先量了磁盘——9,006 字节，文件还是 40 分钟前写的。那个 12,480 是写入那一刻的快照，不是此刻的真相。

从那以后我定了个规矩：**agent 说生成了什么，一律不算数；磁盘上说有，才算有。** 于是把三个常驻 agent 当天汇报的 97 条「已生成」声明逐条量了一遍。命令输出：

```text
DVD: entries=97 exact=79 larger=18 shrink=0 missing=0 remap=2 malformed=0
BYTES-EXIT: 0 (OK)
```

79 精确、18 偏大、0 缩水、0 缺失、2 条路径重映射。看着全绿。但这张干净的表里，藏着三个我踩过的坑。

## 坑一：把「防撒谎下限」当成「验收门槛」

79 条 exact，看着安心。但我从不把「字节对上」当成「产物合格」。

字节数只能证明大小对，证明不了内容对。它能挡住三类拙劣撒谎：空文件冒充产物（0 字节）、字符数冒充字节数（中文一个占 3 字节，两万字长文工具报 7,562、实测 20,271）、自引用冒充实测（把自己的字节写进自己，写完就过期）。低于这条线，一定有问题，所以叫「下限」。

但它防不住「字节完全正确、内容驴唇不对马嘴」的文件。对账工具说 exact，验收该打回。字节数回答「有多大」，不回答「对不对」。所以我的用法是：**字节数用来证伪，不用来证实。**

## 坑二：幽灵产物的三种长相

幽灵产物不是「文件凭空消失」，是「声明和磁盘对不上」的几种错位：

- **明目张胆的 missing**：声明写了路径和字节，磁盘上找不到。最好认，汇总行里 `missing=1`。
- **被重映射遮住的准幽灵**：文件在，但路径搬了家或带了废弃前缀。这次 `remap=2` 就是。脚本先做路径重映射再找，找到了算 remap 不算 missing。**重映射救回来的，是路径问题；救不回来的，才是真幽灵。** 两者要分开报，不然路径漂移会被掩盖。
- **字节对、文件却是旧的**：声明说新报告 8,432 字节，磁盘上真有 8,432 字节的文件——那是三小时前的旧版。只看字节和存在全过，带上 mtime（LastWriteTime）才识破。

字节只是其中一维，配上路径重映射和 mtime 才抓得全。

## 坑三：一条命令核完，还别数错单位

```powershell
python scripts\declared-vs-disk.py --root "<workspace>" --source both --json
```

`--source both` 同时读心跳日志和索引两处声明——agent 声明产物不止一处，只读一个会漏。`--json` 让输出直接进台账；`BYTES-EXIT` 在 shrink 或 missing 大于 0 时非 0，供上游自动拦截。

分类六类：exact / larger（磁盘更大，多是声明后追加写，合法）/ shrink（变小，覆盖嫌疑）/ missing（找不到）/ remap（路径改写后对上）/ malformed（格式写坏）。

两个要点：

1. **按「声明行」计数，不按「文件」。** 97 是声明行数不是 97 个文件，同一文件被两处声明算 2 条。重复本身是要观察的信号，去重数另算、并排放。
2. **18 条 larger 一条都不用修。** 它们几乎全是 append-only 的心跳日志、索引、台账——声明记的是快照，文件后来长大了。盯死 `shrink=0` 和 `missing=0` 两个不变量就够；哪天 shrink 冒出哪怕 1 条、只小 4 字节，都要停下查。

## 写在最后

12,480 对 9,006，差的不只是三千字节，是「agent 的嘴」和「磁盘的手」之间的距离。多 agent 系统里这个距离消灭不了，只能放一把尺子在中间：**每一条「已生成」，都过一遍磁盘实测。** 97 条，一条命令，几秒钟。

三句话带走：

1. 字节数只用来证伪，对上了不等于合格，内容验收另开判据。
2. 幽灵产物分四诊——路径错、搬了家、时间旧、没写，字节只是其中一维。
3. 对账按声明行计数、去重数并排放；larger 多是合法追加，盯死 shrink 和 missing。
