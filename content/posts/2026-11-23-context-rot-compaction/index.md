> 说明：本文所有数字都来自一台本机上真实跑过的记录，命令附在文末可原样复跑。涉及的 agent 以 A / B / C 指代，路径已去掉个人标识，凭据、账号与任何账户金额一律不出现，涉及规模的地方只给相对量。这不是一篇谈模型伦理的文章——它是一次工程复盘，讲的是长任务里「上下文越长、活干得越差」这个反直觉现象，以及我怎么用压缩把它摁住。

## 一、越聊越笨：一个反直觉的现场

有一个迁移任务，我让 agent 连续处理 40 步。前 10 步干净利落，改一处验一处；到第 25 步开始重复问已经问过的问题；第 35 步把最早定下的一条约束忘了；最后交付的东西和最初的目标对不上，返工成本比从头做还高。

我第一反应是模型降级了，怀疑服务端悄悄换了小模型。查了一圈，不是。同一个会话，把前面的历史清掉、只保留最近几步，它立刻又清醒了，回答质量和第 10 步时没有区别。

问题不在模型，在上下文本身。业内有个说法叫「上下文腐烂」（context rot）：随着输入变长，模型对中段和早期信息的注意力被稀释，真正被有效利用的信息密度反而下降。**窗口能塞进去，不等于模型真的用上了。**

三种现象叠在一起，就是这个「越聊越笨」：

- **中间丢失**：长输入的中段最容易被忽略。开头和结尾还记得清清楚楚，中间那一段像根本没读。你把关键约束放在第 5 步，它落在长输入的中前段，恰好是最容易被稀释的位置。
- **注意力稀释**：无关的历史越多，关键信息的权重被摊得越薄。工具返回的原始文本、失败的尝试、废弃的方案，全都占着位置，把真正该遵守的东西挤到角落。
- **错误累积**：早期一个含混的结论被后面每一步引用，每一步都在这个基础上再盖一层，越滚越大。等到发现时，已经分不清哪条是事实、哪条是三层转述出来的幻觉。

这三种都不是偶发，而是长会话的必然产物。所以不能靠「提示词写得更好」来回避，得在机制上处理。

## 二、第一版：无脑截断，把约束一起扔了

最容易想到的办法是截断：输入超过某个长度，就把最老的消息删掉，腾出空间。我按这个思路做了一版，很快翻车。

有一轮任务，用户在第 3 步明确要求「年份字段不能为空」，这是一条硬约束。截断策略按时间从老到新删，跑到第 30 步时这条约束被删掉了——它后面 30 步再没被提起，因为没人需要重复一条已经说过的话。agent 失去这条约束后，交付的字段全成了可空，等我发现已经晚了。

截断的问题不是「删得多」，而是**删得没有结构**。它假设「新的比旧的重要」，但「重要」和「新」是两回事。最早定下的约束、目标、边界条件，往往恰恰是最重要的，却最先被删。剩下的是一堆最近的、细碎的、彼此无关的操作记录——看起来满满一屏上下文，其实把骨架抽走了。

更隐蔽的是，截断之后 agent 自己并不知道丢过东西。它不会说「我忘了」，它会基于剩下的残缺上下文，非常自信地继续往下做。**丢失是无声的**，这才是最麻烦的地方。

我意识到，压缩不能是「删」，得是「提炼」。要把不能丢的东西单独挑出来焊死，把可以丢的东西归档留档，而不是一刀切。

## 三、第二版：三段式压缩

我把压缩改成三段，每段职责单一，互不干扰：

1. **结构化状态卡**：把当前目标、已完成、待办、关键约束、已定决策抽成固定字段。这段永不删除，每轮都完整带过来。
2. **摘要链**：每一步完成后追加一条一行摘要，串成一条链。老的摘要可以合并压缩，但字段不能丢。
3. **原文归档**：原始对话和工具返回落到磁盘文件，正文上下文里只留路径和行号，需要时再取回。

状态卡的字段是写死的，大致长这样：

```go
type StateCard struct {
    Goal        string   // 当前目标，唯一
    Constraints []string // 硬约束，只增不减
    Done        []string // 已完成步骤摘要
    Next        []string // 待办
    Decisions   []string // 已定决策 + 理由
}
```

关键在 `Constraints` 只增不减。压缩时可以对 `Done` 和摘要链做合并，但约束字段必须原样带到下一段上下文。这是防「截断把约束删了」的核心机制——硬约束有一个专属的、不参与裁剪的位置。

`Decisions` 要连理由一起存。只记「选了方案 A」没用，下一轮遇到同样局面它会重新纠结一遍；记了「选 A 因为 B 不满足某约束」，它才知道这个决定不是随便做的，不会反复推翻。

摘要链的作用是让 agent 在无原始对话的情况下，也能知道「发生过什么」。它不全，但够用——每一步一行，谁做了什么、结果如何，串起来就是一条可追溯的线。

## 四、什么时候压：按事件，不只按长度

我一开始按输入长度阈值触发压缩，到线了就压。用了一阵发现不够——有些任务在阈值之前就已经开始跑偏，等长度到线，错误已经滚了好几层。

改成按事件触发，两类信号任一命中就压缩：

- **长度信号**：输入接近窗口上限的某个比例（留足余量，别顶到极限才动手）。
- **语义信号**：agent 开始重复提问、开始引用含混结论、连续几步没有实质推进。

```text
触发条件 = 长度超阈 OR 重复提问>=2 OR 连续无推进>=3
压缩输入 = 状态卡 + 最近 N 步原文 + 摘要链
压缩输出 = 更新后的状态卡 + 合并摘要 + 原文归档路径
```

语义信号比长度信号更早、更准。重复提问说明它把刚才的信息弄丢了；连续无推进说明它陷在某个死结里，这时候与其让它继续空转，不如停下来压缩、把状态重新摆清楚再出发。

压缩的产物要落盘，不能只在内存里换。落盘的好处是可回退：这次压坏了，能退到上一份状态卡重来。内存里换掉的上下文，一旦压错就再也找不回来。

## 五、判据：压缩后必须能回答三个问题

压缩做得对不对，不能靠「感觉清爽了」。我定了三个问题，压缩后的上下文必须能当场答出来：

1. 现在要干成什么？（`Goal` 唯一且非空）
2. 哪些约束不能破？（`Constraints` 完整，条数不减）
3. 下一步做什么？（`Next` 非空且可执行）

```text
RESULT: COMPACTION_CHECK = 目标唯一=Y / 约束不减=Y / 待办非空=Y
```

三问任一答不上，判压缩失败，回退到上一份状态卡重来。这条判据是机器可判的——三个字段都是结构化的，数一数、比一比就知道，不用人去读整段上下文凭感觉评估。

把主观判断写成退出码，这个思路在这里同样成立。「压缩有没有丢东西」听起来很主观，但拆成三个结构化字段之后，它就是一个可以自动跑的断言。凡是能写成断言的，就不该再靠人盯。

## 六、踩坑：摘要里也会长出幻觉

摘要不是无损压缩。它由一个模型来写，就必然带模型的毛病。我遇到过一次：agent 在摘要里写「已完成字段校验」，但原文里其实只是写好了校验函数，根本没有运行。摘要把「写了」压成了「完成了」。下一个上下文拿着这条摘要，以为校验这关已经过了，直接往下走。

这类「摘要幻觉」比原始对话里的错误更难发现——它是转述出来的，读起来非常顺、非常像真的，而且离证据已经隔了一层。

修法是给摘要加**证据锚点**：每条 `Done` 必须带一个可核验的引用，要么是文件路径加行号，要么是一条命令加它的输出。没有锚点的摘要不许进状态卡。

```text
坏摘要: 已完成字段校验
好摘要: 字段校验函数已写入 <模块路径>:L120，测试尚未运行
```

这个约束和「凡声称落盘先报字节数」是同一个思路：凡是声称完成的，附一个外部可核验的锚点。摘要也一样，不能只写结论，要写结论的证据在哪。做不到这一点，压缩就是在给幻觉制造温床。

## 七、成本账：压缩不是免费的

压缩本身要消耗输入——你得把状态卡和最近若干步喂给模型，让它产出新摘要。所以它不省钱，只是把成本从「每一步都背着全量历史」挪到「低频的压缩动作 + 常驻的精简上下文」。

一笔实测的账（相对量，不含任何具体金额）：

```text
不压缩: 末步输入 = 全量历史，规模随步数线性上涨
压缩后: 末步输入 ≈ 状态卡 + 最近N步 + 摘要链，趋于常数
压缩自身开销: 每次约一遍状态卡的量，触发频率低
```

结论很直白：短任务（十几步以内）不值得压，压缩的固定开销占比反而高，还会引入摘要幻觉的风险；长任务、循环任务、需要跨天续跑的任务，压缩是刚需，不压必烂。

分界线不在步数，而在「上下文是否已经开始稀释关键信息」。判断方法就是第四节那两类信号：出现了就压，没出现就别折腾。

## 八、四条能抄走的规矩

这场折腾下来，我把「长任务越聊越笨」从玄学改成了可操作的工程，抽象出四条能直接抄走的东西：

1. **别无脑截断。** 按时间删会把最早的硬约束删掉，而它往往最重要。丢失还是无声的，agent 不会告诉你它忘了。
2. **压缩要结构化。** 状态卡字段写死，约束只增不减，摘要必须带证据锚点。提炼，不是删减。
3. **按事件触发，不只按长度。** 重复提问、连续无推进都是跑偏信号，比长度阈值更早、更准。压缩产物落盘，可回退。
4. **压缩后跑三问判据。** 目标唯一、约束不减、待办非空，三个结构化断言，机器可判，不靠感觉。

回到开头那个 40 步迁移。用上三段式压缩后，它再没在第 35 步忘约束——因为约束在状态卡的专属字段里，根本不参与裁剪。**上下文会腐烂，但你可以把不该烂的那部分单独钉住。** 这不是让模型变得更聪明，而是承认它会腐烂，然后围绕这个事实设计机制。工程上真正可靠的做法，从来不是赌模型这次不出错，而是让出错的东西在结构里无处藏身。
