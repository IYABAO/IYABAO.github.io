# RAG 评测：离线指标与线上效果的鸿沟

RAG 项目最经典的场景：**离线 recall@5 90%，上线后用户还是骂"答非所问"**。为什么离线指标好看、线上效果拉胯？

因为 RAG 评测有三层，大部分项目只测了第一层。

## 一、RAG 的评测分层

```
第 1 层：检索质量（找得对不对）
第 2 层：生成质量（答得好不好）
第 3 层：端到端效果（用户满不满意）
```

## 二、第 1 层：检索质量

### 指标

```
Recall@K：正确答案出现在前 K 条的比例
Precision@K：前 K 条里多少是有用的
MRR：第一个正确答案的排名
NDCG：带相关性权重的排序质量
```

### 评测集

```json
{
  "query": "简历缓存一致性方案",
  "gold_docs": ["doc-123", "doc-456"],   // 正确答案
  "relevant": ["doc-123", "doc-456", "doc-789"]
}
```

### 为什么 recall@5 90% 了线上还差

**鸿沟 1：评测集和真实分布脱节**

```
评测集：精心构造的问题（清晰、完整）
线上：真实问题（口语化、残缺、多义）
  "缓存怎么搞的" —— 评测集里没有这种问题
```

**解法**：线上问题采样进评测集（每天自动抽 1% 真实 query，人工标注）。

**鸿沟 2：只测"找没找到"，没测"找到的有没有用"**

```
Recall 高 = 正确答案在列表里
但 LLM 看到的前 3 条可能：
  1 条正确答案 + 2 条高相似度噪音
→ LLM 被噪音带偏 → 答非所问
```

**解法**：加"噪音比例"指标（前 K 条中无用的比例），和重排质量。

## 三、第 2 层：生成质量

### 指标

```
忠实度（Faithfulness）：回答是否完全基于检索内容（不幻觉）
相关度（Relevance）：回答是否针对问题
完整性（Completeness）：要点是否答全
格式正确性
```

### 评测方法

```
1. LLM-as-Judge：强模型按维度打分（检索内容 + 问题 + 回答）
2. 事实核对：回答中的每个事实能否在检索内容中找到
3. 引用检查：回答是否带来源、来源是否真实
```

```python
# 事实核对（判断幻觉的核心）
def check_faithfulness(answer, contexts):
    facts = extract_facts(answer)          # 拆事实
    unsupported = [
        f for f in facts
        if not any(f in ctx for ctx in contexts)   # 检索内容里没有
    ]
    return 1 - len(unsupported) / len(facts)       # 忠实度
```

### 关键：生成质量评测必须"看检索内容"

```
❌ 只给"问题 + 回答"让 LLM 打分（回答错没错，不依赖 RAG 质量）
✅ 给"问题 + 检索内容 + 回答"三件套（才能发现：回答是好的，但没用上检索内容）
```

## 四、第 3 层：端到端效果

### 指标

```
用户可感知的：
  满意度（点赞/点踩）
  任务成功率（问答闭环完成）
  放弃率（没答明白就走）
  人工兜底率（转人工的比例）
业务价值：
  转化率 / 工单减少 / 成本下降
```

### 端到端评测集（线上回流）

```
用户点踩的问答 → 自动入"问题池" → 定期人工标注 → 补进评测集
```

**闭环**：线上差评 → 进评测集 → 复现问题 → 修（检索/重排/生成）→ 验证 → 回归。

## 五、三层的关系与优先级

```
第 1 层（检索）错了 → 第 2、3 层必然错 → 先修检索
第 2 层（生成）错了 → 第 3 层错 → 再修生成
第 3 层（用户）反馈 → 反哺第 1、2 层

优先级：
  先让检索"找得到"（Recall 高）
  再让生成"用得上"（Faithfulness 高）
  最后看用户"满不满意"（业务指标）
```

**每个指标的优化动作**：

```
Recall 低 → 调 embedding / 换模型 / 加混合检索
噪音多 → 加重排（Rerank）/ 调阈值 / 查重
Faithfulness 低 → 收紧引用 / 限制上下文 / Prompt 约束
Relevance 低 → 问题重写 / 意图识别 / 检索改写
```

## 六、踩坑记录

1. **评测集 100 条就敢下结论**：指标波动大 → 至少 300-500 条 + 固定版本
2. **只看 Recall 不看噪音**：Recall 90% 但 top3 里 2 条噪音 → 加噪音率指标
3. **LLM 评分偏置**：偏好长回答 → 多模型投票 + 人工抽查校准
4. **线上回流不及时**：用户骂了半个月才进评测集 → 差评自动入池 + 每周标注

## 总结

RAG 评测的核心认知：

1. **三层评测**：检索（找得对）→ 生成（答得好）→ 用户（满不满意）
2. **鸿沟的根源**：评测集 ≠ 真实分布，离线指标 ≠ 用户感知
3. **评测必须看上下文**：生成评测要带"检索内容"看，才发现真问题
4. **闭环回流**：线上差评进评测集，修复后回归验证

**RAG 评测的目的不是"证明它好"，是"知道它哪里不好、改哪里"。** 三层指标对上了，优化才不是玄学。
