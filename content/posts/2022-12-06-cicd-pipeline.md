# CI/CD 流水线：从手动发布到一键上线

发布是最高危的操作：手动发布 = 靠人记步骤 + 靠运气不犯错。CI/CD 的价值不是"自动化"三个字，是**把发布变成"可重复、可回滚、可审计"的流程**。

## 一、手动发布的痛点

```
手动发布流程：
  1. 本地构建 → 2. 传包到服务器 → 3. 停服 → 4. 替换文件 → 5. 起服 → 6. 验证
  （或：登录服务器 → 拉代码 → 编译 → 重启）

问题：
  1. 环境差异：本地能编，服务器编不过
  2. 步骤遗漏：漏了迁移脚本 → 上线后数据错
  3. 不可回滚：新版有问题，旧包没留
  4. 人肉操作：凌晨发布，手抖 = 事故
```

## 二、流水线的三个阶段

```
CI（持续集成）：提交代码 → 自动构建 + 测试
CD（持续交付）：构建产物 → 自动部署到环境
CD（持续部署）：测试通过 → 自动发布生产

演进：CI → CI+CD（交付到测试）→ CI+CD（全自动）
```

## 三、流水线设计（GitHub Actions 示例）

```yaml
name: CI/CD
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:                      # CI：提交即测试
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with: { go-version: '1.24' }
      - run: go vet ./...
      - run: go test -race ./...
      - run: go build ./...

  deploy:                    # CD：合并即部署
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - run: docker build -t registry/xx:${GITHUB_SHA::7} .
      - run: docker push registry/xx:${GITHUB_SHA::7}
      - run: kubectl set image deploy/xx app=registry/xx:${GITHUB_SHA::7}
```

## 四、流水线的关键设计

### 1. 产物不可变（构建一次，处处使用）

```
✅ 同一个镜像，测试环境验证过 → 生产用同一个（不许重新构建！）
❌ 生产重新构建 = 测试白测（代码可能不同）
```

### 2. 阶段门禁（Gate）

```
代码检查（lint）→ 单元测试 → 构建 → 部署测试环境
→ 冒烟测试（关键接口）→ 人工确认（可选）→ 部署生产
→ 生产验证（健康检查）→ 完成

任一阶段失败：流水线停住，不放行
```

### 3. 回滚机制

```
✅ 部署带上版本号（镜像 tag / 发布记录）
✅ 一键回滚：kubectl rollout undo / 切回旧镜像
✅ 回滚后自动通知（谁发布的、什么时候、为什么回滚）
```

### 4. 环境隔离

```
dev（开发）→ test（测试）→ staging（预发布，和生产一致）→ prod（生产）
禁止：测试环境没验证直接上生产
```

## 五、踩坑记录

1. **测试阶段没跑全**：CI 只跑 build 不跑 test → 错误进生产 → CI 里 test 是必过门禁
2. **构建产物不一致**：CI 和本地构建结果不同（版本/依赖差异）→ 用锁文件（go.sum/package-lock）+ 固定构建镜像
3. **密钥进代码**：部署密钥写在流水线 YAML → 泄漏 → 用 Secrets（GitHub Secrets / CI 平台的密钥管理）
4. **回滚链路没演练**：有回滚按钮，没演练过 → 真出事了按钮没用 → 回滚要演练（每月一次）
5. **流水线变长**：一次提交等 20 分钟 → 反馈慢 → 拆分：快速检查（5 分钟）+ 深度测试（定时跑）

## 六、流水线的指标

```
✅ 部署频率（越频繁越好：小步快跑）
✅ 变更前置时间（提交 → 上线耗时，目标 < 1 天）
✅ 变更失败率（上线的故障比例，目标 < 15%）
✅ 恢复时间（出故障到恢复，目标 < 1 小时）
```

**这四个指标是 DORA 研究的核心**：部署快 + 失败少 + 恢复快 = 健康交付。

## 总结

CI/CD 的核心认知：

1. **CI 管"提交即验证"**：构建 + 测试 + 门禁
2. **CD 管"验证即部署"**：产物不可变 + 环境递进
3. **回滚是标配不是备选**：版本化 + 一键回滚 + 演练
4. **四指标看健康度**：部署频率、前置时间、失败率、恢复时间

**CI/CD 的终极形态不是"全自动发布"，是"发布低风险"。** 自动化只是手段，让发布"快而稳"才是目的。
